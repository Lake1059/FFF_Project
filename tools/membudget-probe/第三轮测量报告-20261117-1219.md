## 臂 1：预取命中率（图片目录 40 张）

命令：`membudget-probe.exe --images C:\PLAN\3FCompare\3fp\build\_prefetch_imgs 40`
日志：`probe3-r3-images.log`，退出码 0。

```
[probe] env MEMARB=1 CAP_MB=- AUDIO_CAP_KB=-
[probe] images found=40
[probe] images-summary opened=40 ready=40 hits0=0 hits1=15 misses0=0 misses1=25 lru0=0 lru1=0 trim0=0 trim1=0 hitrate=0.375
[probe] prefetch hits=15 misses=25 lru=0 trim=0 cached=41473185 budget=268435456
```

| 指标 | 值 |
|---|---|
| opened / ready | 40 / 40（全部 Ready） |
| Δhits / Δmisses | 15 / 25 |
| hitrate | **0.375** |
| lru / trim | 0 / 0 |
| cached / budget | 41,473,185 B（≈39.6 MiB ≈ 15 帧 × 2.76 MiB）/ 256 MiB |

**逐张命中曲线**：img_001 冷启 miss；img_002~img_016 连续命中（hits 0→15）；**从 img_017 起 hits 冻死在 15，后 24 张全 miss**。

**判定：hitrate=0.375 < 0.5，按字面阈值 FAIL，但根因已定位且不是缓存缺陷**：
内核 `SetPlan` 解析计划路径时有硬上限 `paths.size() < 16u`（`PrefetchService.cpp:841`）——计划最多只收 **16 条路径**（当前文件 + 15 个邻居）。探针送了 40 条，内核只取前 16 条。步行走到 img_017 时，它已不在任何计划的 16 条窗口内，永不被预热。这是 ABI 上限，不是预算问题。

**lru/trim=0 的说明**：缓存 40 MiB vs 预取预算 256 MiB（status.budgetBytes 直读 268435456），15 帧远未顶到预算；单帧 2.7 MiB × 理论上限 94 帧——**40 张 1280×720 静帧在本机预算下确实压不到 LRU/trim 触发**，与预估一致。

**内核侧交叉核对**：日志中**没有任何 `[prefetch]` trace 行**（`FFF_MEMARB_TRACE=1` 下 prefetch 通道未输出），内核侧四计数无法从 trace 核对，以上数字全部来自探针 `GetPrefetchStatus` 直读。

## 臂 3：预算上限开关 + Σfloor 三级降级（`fx_bgr0_1920x1080.mkv`，8 s，profile 2）

命令：`membudget-probe.exe <媒体> 8 2`，`FFF3FP_MEMARB_CAP_MB` 梯度。日志 `probe3-r3-floor-<mb>.log`。

| cap(MiB) | 退出码 | precheck 主文件 | 结果 |
|---|---|---|---|
| 0 | 0 | `step=0 sum=94MiB budget=~1900MiB` | step=0 正常开（8 线程 3 帧） |
| 256 | 0 | `cap-test computed=1933mib cap=256mib` | step=0 正常开 |
| 96 | 0 | `precheck step=0 sum=94MiB budget=96MiB` | **step=0 成功**（94 ≤ 96） |
| 64 | 0 | `precheck step=2 sum=55MiB budget=64MiB` | **step=2 成功**（4 线程 2 帧） |
| 60 | 0 | 同上 | step=2 成功 |
| 56 | 0 | `precheck step=2 sum=55MiB budget=56MiB` | **step=2 成功**（55 ≤ 56） |
| 52 | 7 | step=2 sum=55 > 52 | **step=3 拒绝** |
| 48 / 32 / 24 / 16 | 7 | 同上 | step=3 拒绝 |

**关键证据原文**：
- cap 生效（mb=256）：`[arbiter] cap-test computed=1933mib cap=256mib`（computed 原始值 ~1.9 GiB，最终 budget 被压到 cap）。
- step=2 成功档（mb=56）：
  ```
  [arbiter] precheck step=2 sum=55MiB budget=56MiB frame=1920x1080 7.9MiB
  [arbiter] floor-step step=2 threads=4 frames=2
  [arbiter] floor-step degrade step=2 reason=Σfloor still over budget after 2 video frames: decode ladder 8->4 threads
  ```
  即 step=0 的 Σfloor（94 MiB）超出 56 → 降级到 step=2（4 线程 2 帧，Σfloor=55）后成功打开。
- step=3 拒绝档（mb=48，exit=7）：
  ```
  [arbiter] floor-step step=3 threads=4 frames=2
  FAIL open-refused state=Failed last-error=Memory budget refused this file: floors 55 MiB exceed the pool's 48 MiB even after degrading to 2 video frames and 4 decode threads (1920x1080, 7.9 MiB per frame). Use hardware decoding, or a smaller picture or lower bit depth.
  ```

**判定**：
- ✅ step=1（成功打开，pool≥96 档 step=0）、step=2（成功打开且 threads 8→4 cap 到 4，pool 56~64 档）、step=3（拒绝，pool≤52）三档实机证据全部拿到。
- ⚠️ **本机未观察到 step=1 中间档**：降级链是 step=0（Σfloor 94 MiB）直接跳到 step=2（Σfloor 55 MiB），没有出现过 step=1 的提交。两档边界：step0→step2 在 64~96 MiB 之间，step2→step3 在 52~56 MiB 之间。
- ⚠️ `[arbiter] floor-step threads capped X -> Y by precheck` 这行**全程未出现**；等价证据是 `degrade step=2 reason=... decode ladder 8->4 threads`。

## 臂 4：限额抖动压测（两媒体 × cap 梯度 × 60 s，profile 2）

命令：`membudget-probe.exe <媒体> 60 2`。日志 `probe3-r3-jitter-<fx|vidA>-<mb>.log`。
**口径说明**：每次运行探针末尾会重开邻居文件产生第二个 arbiter 会话（计数器重置）；下表取**主媒体 60 s 的第一个 `[arbiter] budget` 行**（邻居会话仅 1.5 s，不计）。

| 媒体 | cap(MiB) | total | granted | recompute | suppress | flap | queued 区间 |
|---|---|---|---|---|---|---|---|
| fx 1080p | 0 | 1826 | 583 | 215 | 0 | **46** | 0..6 |
| fx 1080p | 160 | 160 | 160 | 195 | 0 | 0 | 0..6 |
| fx 1080p | 96 | 96 | 96 | 195 | **484** | 0 | 0..1 |
| fx 1080p | 64 | 64 | 64 | 210 | **899** | 0 | 0..1 |
| vidA 720p | 0 | 1911 | 513 | 227 | 0 | **47** | 0..4 |
| vidA 720p | 160 | 160 | 160 | 227 | 0 | 0 | 0..4 |
| vidA 720p | 96 | 96 | 96 | 225 | 0 | 0 | 0..4 |
| vidA 720p | 64 | 64 | 64 | 224 | 0 | 0 | 0..4 |

**判定（按写死阈值：recompute ≤ 30、flap = 0）**：
- **recompute 全部 195~227（≈3.3~3.8 次/s），没有任何一档 ≤ 30**——按字面阈值全部不达标。但结合 suppress 列读：recompute 是内核内部重算评估次数（无 cap 基准下也有 215~227），**真正的"抑制生效"信号是 suppress**：只有 fx 在 96/64 MiB 紧预算下 suppress 才冲到 484/899，即死区闸门在预算紧、负载重时大量拦下重算请求。
- **flap**：无 cap 基准 46/47（升档后 4 s 内又降真的发生）；**一加 cap（160/96/64）所有档位 flap=0**——预算上限开关把抖动环消除了。
- 按要求如实写：**vidA 四档 suppress 全 0**——720p+AAC 负载轻，限额根本没被推着动，抑制无从体现，不能算"抑制成功"；fx 在 0/160 档 suppress 也为 0，同理。
- 队列幅度：fx 松预算 0..6、紧预算 0..1；vidA 全档 0..4。与上一轮 0..4 量级一致。

## 臂 5：池 rung 预升（pre-climb）是否出现

对 8 份臂 4 日志 grep `[ladder] pre-climb`：**全部为 0 次，预升从未触发**。

上下文证据（fx-64 日志）：
```
[ladder] frame pool holds at 128 MiB gate=decode bound=0.74 starved=1.00 dropped=0 uploadMs=4.21 frameMs=16.67
[ladder] window decoded=106 presented=104 presentedFps=51.98 sourceFps=60.00 missingRate=1 noSpare=1 stalled=0 saturated=311/421
```
`bound=0.74`——队列贴的是**下界（starved=1.00）**，离 pre-climb 要求的"整窗贴死上限（boundRatio ≥ 0.95）"方向相反，所以预升条件从未挣到。

与上一轮的关系：上一轮"重算恒 0 = 授予量不移动"，本轮 recompute≈200（授予量在频繁重估），但队列始终饥饿而非贴顶——**根因不同：本轮不是授予量不动，而是软解欠供把队列压在下界，上界触发条件（bound≥0.95）自然不发生**。

## 失败 / 未构造出来的项（显式列出）

1. **臂 1 hitrate=0.375 < 0.5**：未达标。根因是内核计划路径 16 条硬上限（ABI），非缓存缺陷；若要更高 hitrate，需内核放宽 `SetPlan` 的 16 条限制或探针只送 15 个邻居。
