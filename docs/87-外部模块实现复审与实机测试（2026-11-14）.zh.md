## 本轮确认并修复的缺陷

| 编号 | 严重度 | 缺陷 | 证据 | 修复 |
|---|---|---|---|---|
| R1 | 高 | 中性音频表缓存会在撤表/重开后复用已销毁 context | `NeutralExternalModule` 原用 `_音频表已取` / `_直通表已取` 缓存；原生 `PlayerSession::SetAudioRenderPlug` 把旧表放入 `audioPlugRetired_`，由 worker `destroy(context)`；`AudioPassthroughLane::InstallTable(nullptr)` 立即 `destroy(context)` | 删除缓存，`尝试取音频渲染表/直通表` 每次重新 `getCapability` 握手；保留所有权只在“内核接受后”转移 |
| R2 | 高 | 中性“解锁码已接受未落盘”实例被临时释放，授权丢失 | `外部模块接口.提交解锁码` 原在 `Finally` 无条件 `Dispose`；模块票据未落盘时授权只活在模块镜像内存，`FreeLibrary` 后下一次探测仍锁定 | 增加模块级保留列表；仅 `已接受未落盘` 保留实例到进程结束，其余结果正常释放 |
| R3 | 高 | `FFF3FP_MODULE_DIR` 只作用于中性搜索，legacy 回退不认 | 实机 auto + `FFF3FP_MODULE_DIR` + `FFF3FP_EXTERNAL_MODULE_FILE=NoSuch.dll` 时进程不加载任何外部模块 | 新增 `旧件目录()`，`探测/尝试装载/模块在盘上/提交解锁码/取状态文本` 统一把通用目录传给 legacy |
| R4 | 高 | legacy adapter 的授权状态/文本/提交没有绑定实际装载目录 | adapter 原调用 `色彩变换模块接口.探测(原因)` / 全局 `取状态文本` / 全局 `提交解锁码`，不带 `_旧` 的目录；目录覆盖或临时目录装载时会被另一枚/默认路径模块回答 | 使用装载时命中的实际路径；`色彩变换模块实例` 新增 `模块路径`，adapter 以实际目录贯穿授权三入口 |
| R5 | 中高 | legacy 搜索没有 `Modules` 子目录，auto 下旧件放在 `Modules` 找不到 | `候选路径` 原只查进程目录/`AppContext.BaseDirectory` 根目录；新通用搜索序已把 `Modules` 作为首选子目录 | 两处基准目录都按 `Modules → 根目录` 顺序搜索，并补回归 |
| R6 | 中高 | `外部解锁结果` 把“够不到/无法提交”折叠成“被拒”，`Form1` 的 `Case Else` 不可达 | 门面枚举原只有 被拒/已接受/已接受未落盘；模块缺席、无 Authorization、未知返回码都会走“被拒”，用户会白试 5 次 | 新增 `无法提交 = 3`；映射 legacy `够不到`、中性无 Authorization、未知返回码；`Form1` 的 `Case Else` 恢复可达 |
| R7 | 中 | 发布 staging 的外部模块扫描不递归，`Modules\` 子目录会漏过 | `发布3FP.ps1` staging、`发布3FP单文件.ps1` staging、`检查外部模块中性.ps1` 发布目录仍用顶层 `-File` | 三处全部改为 `-File -Recurse`；初始输出检查也已递归 |
| R8 | 中 | 中性授权/状态/提交与 Dispose 存在读取竞态；表指针转换失败会抛 | 授权方法只在部分路径检查 `_已释放`；`PtrToStructure` 没有局部 try | 授权状态/文本/提交/读取注入状态统一在 `_锁` 内检查并调用；两张表读取加局部异常处理 |

### 修复后的关键纪律

- 音频表：握手只代表拿到表，**内核接受**才 `Mark...` 所有权；撤表/替换时内核会销毁 context，所以宿主每次交付都必须重新握手。
- 解锁：`已接受未落盘` 是“本次进程可用、重启要重输”，不是失败；必须保留模块镜像，不能把刚授予的内存态连同 `FreeLibrary` 一起丢掉。
- 目录：中性、legacy、发布检查必须使用同一套搜索序：显式目录 / `FFF3FP_MODULE_DIR` → `Modules` → 进程目录 → `AppContext.BaseDirectory` → 裸文件名（legacy 兼容顺序保留）。
- 结果：`被拒` 只表示“码不对”；模块缺席/无入口/未知返回码必须是 `无法提交`，不能诱导用户重试。

## 复审中确认但本轮不修的剩余项

1. **legacy 合成 descriptor 固定声明四项能力**
   - `LegacyColorModuleAdapter` 的 descriptor 固定写 `授权 | 音频渲染 | 音频直通 | 处理器`，但旧模块实际可能只导出一部分。
   - 当前 UI 主要用显示名和 `处理器可用`，尚未按 descriptor 分流；未来若按能力位决定 UI/通路，会误判。
2. **auto 下“中性已装载但能力不可用”不回落 legacy**
   - `尝试装载` 只要中性模块装载成功就返回，即使没有 Authorization/处理器/音频；只有中性装载失败才回退。
   - 这是当前“中性文件优先”的设计口径；如果允许“空壳中性文件”存在，需要明确是否应视为失败。
3. **中性 `探测/显示名称/提交解锁码` 每次调用重新 LoadLibrary/FreeLibrary**
   - `Form1` 解锁轮询 1 秒一次、60 秒窗口会重复装载；功能正确但存在 UI/性能开销。
   - 若后续把轮询改为“启动时一次探测 + 事件驱动”，可消除。
4. **中性 `Dispose` 在所有权转移后永久保留 DLL 句柄**
   - 这是为了防止内核仍持有模块代码段函数指针；当前一个会话一份实例，属保守卸载。
   - 需要确认长期生命周期预期（是否允许进程内多次会话后句柄累积）。
5. **未跑完整播放压力与 Application Verifier/PageHeap**
   - 本轮只做启动/装载/解锁 UI 和 100 次模块装载生命周期；未对真实 `打开→播放→seek→换文件→关闭` 做 Application Verifier 验证。
   - 音频表撤/开的空间音频真实 UI 切换也未做长跑；静态路径已按内核 `destroy` 语义修复。
6. **`Modules` 搜索只覆盖进程目录/`AppContext.BaseDirectory`**
   - 若用户把 `FFF3FP_MODULE_DIR` 指向一个根目录，并把 legacy 放在该目录下的 `Modules\`，当前不会查 `env\Modules`；只查 env 根目录 + 进程/应用目录的 `Modules`。
   - 需要确认通用目录是否也应包含其 `Modules` 子目录。
7. **发布脚本剩余的顶层扫描**
   - `发布3FP.ps1` 最终文件计数仍用顶层 `Get-ChildItem -File`；`发布3FP单文件.ps1` 的 `UnexpectedFiles` 也只看顶层（子目录用于 AI worker，属预期）。
   - 这些不是外部模块护栏，但会让“文件数/散装内容”报告与磁盘实际不完全一致。
8. **既有构建/工具链问题**
   - `tools\check_ffmpeg_variant.py` 缺失，散装发布时 FFmpeg 变体判定未执行。
   - `FFF.Native\x64\Debug\FFF.Native.dll` 当前是 Release 副本，不是正式 Debug 原生产物。
   - `tools\构建3FP.ps1` 完整 Debug 仍可能失败于 vcpkg `libiconv:x64-windows` 的 `make` 阶段；本轮未重跑完整原生构建。
