## 三、P0 / P1 详述

### P0-1 IEC 61937 端点的 `nBlockAlign` 用错字节宽度（阻断源码直通）

**事实链**

1. 契约：模块 `pack()` 输出的是 **s16le ready** 的 burst（每样本 2 字节），`linkChannels` 只取 **2 或 8**。
   `FFF.Player.AudioPassthrough.h:56-57, 73`
2. 内核建端点时把块对齐写成每声道 **4 字节**：

```cpp
// WasapiRenderer.cpp:1248-1252
exclusiveCandidate.Format.wBitsPerSample = 16;
exclusiveCandidate.Format.nBlockAlign = static_cast<WORD>(4 * exclusiveCandidate.Format.nChannels);
exclusiveCandidate.Format.nAvgBytesPerSec = decided.linkSampleRate * exclusiveCandidate.Format.nBlockAlign;
```

3. 这个 `nBlockAlign` 随后被当作渲染器的字节计量单位：

```cpp
// WasapiRenderer.cpp:1379-1380
outputBlockAlign_ = activeFormat->nBlockAlign;
...
// :1584-1586   burst 队列按 outputBlockAlign_ 折算成帧
copied = std::min(wantedFrames * outputBlockAlign_, bitstreamQueuedBytes_);
renderedFrames = copied / outputBlockAlign_;
```

**后果（二者必居其一，都不是可用状态）**

- **A：端点拒绝**。`WAVEFORMATEXTENSIBLE` 要求 `nBlockAlign == nChannels × wBitsPerSample/8`；16 bit/2ch 应为 4，这里给 8，`IsFormatSupported` 基本必然失败 → `bitstreamFormatRejected_ = true` → `FallBackFromPassthrough("endpoint-unsupported")`。表现为**任何设备上源码直通都不生效**，界面徽章永远停在三态里的前两态。
- **B：端点容忍**。`nAvgBytesPerSec` 也被写成 2 倍（48k/2ch 变成 384000），播放时钟按 8 字节/帧折算，实际字节只有 4 字节/帧 → 载体以 **2× 速率**被消耗，burst 节奏与 IEC 61937 不符，接收端无法锁定；同时快照里的缓冲量/位置以 2 倍偏差上报。

**正确写法**：`nBlockAlign = 2 * nChannels`（2ch→4，8ch→16），`nAvgBytesPerSec = linkSampleRate * nBlockAlign`。若确有必要走 32 bit 容器，则 burst 必须按 32 bit 打包，而契约明确是 s16le，两条路不能混。

补充说明：**具体失败形态（被拒 vs 被接受但倍速）取决于驱动与音频引擎的校验严格程度**，我无法在不实机的前提下判定落在哪一支；但"声明 16 bit、块对齐却按 4 字节/声道"在同一个 `WAVEFORMATEXTENSIBLE` 里就是自不自洽的，这一点无需实机即可确认。修复后请务必用 `IsFormatSupported` 的返回码 + 快照 `audioPassthroughActive` + `burstsRendered` 三者一起验证。

**为什么这条把 PR 的"已实测"结论一并否掉**：交接文档已注明正文里的 `45 tick`、`probe 21/21` 等数字未经复核。这条缺陷意味着**直通链在真实端点上的正向路径从未被验证过**（要么从未进入 engaged，要么进入了但节奏错）。建议作者用 `IsFormatSupported` 打印 HRESULT 做一次最小验证，再谈直通链的实测结论。

### P1-1 三个音频导出走静态 `DllImport`，破坏"缺导出就降级"的既定性质

同一个文件里存在两套解析方式：

| 导出 | 解析方式 | 位置 |
|---|---|---|
| `FFF3FP_GetPresentationCounter`、`Set/GetPrefetchPlan`、`GetPrefetchStatus`、`Begin/EndStartupCpuPlacement`、`GetCpuPlacementSnapshot`（共 8 个） | `解析可选导出`（GetProcAddress，缺席返回 Nothing） | `播放器原生接口.vb:1398-1405` 等 |
| `SetAudioBinauralPolicy`、`GetAudioBinauralStatus`、`SetAudioPassthroughApi`、`SetAudioPassthroughMode`、`GetAudioPassthroughState`（共 5 个） | 静态 `DllImport` | `播放器原生接口.vb:1696-1735` |

**这不是"死代码洁癖"，有一条真实可达的混版路径**：`SnapshotVersion` 从第一笔提交 `5d88c1b` 起就是 23，而 `SetAudioBinauralPolicy` 是第 6 笔 `cb1ba13` 才加的。也就是说**存在一串"版本 23 但没有这些导出"的中间内核构建**——它们能通过宿主的版本探测，随后在首次调用时抛 `EntryPointNotFoundException`。

**当前后果被两层"兜底"掩盖，但副作用真实存在**

- `设置音频直通模式` 自己 `Catch ex As EntryPointNotFoundException`（`播放器会话.vb:839-844`）→ 手动切直通时安全。
- `安装音频直通插槽核心`（`:808-830`）的 `FFF3FP_SetAudioPassthroughMode`（`:820`）**没有本地 catch**，靠外层 blanket catch 兜住：
  - 会话启动 `:246` → 被 `:260` 的 `Catch ex As Exception` 吞掉，但**同一 Try 块的后续动作（`:252-257` 启动注入泵）被跳过**；
  - 解锁后唤醒 `:301` → 被 `:309` 吞掉并 `Return False`，**注入泵不启动**。
- 最终表现：直通静默不可用（符合设计），同时**色彩模块的注入泵也一起没起来**，用户看到的是一只"半启动"的模块。这是跨功能的副作用，不是直通自己的失败。

**修法（二选一）**

1. 把 5 个导出统一改成 `解析可选导出`，与同文件其余 8 个一致（推荐，改动最小）；
2. 或在 `:820`/`:821` 加本地 `Catch ex As EntryPointNotFoundException → Return`，让失败不越出插槽安装函数。

顺带建议：把"内核可选能力探测"收敛成一个显式能力位（内核已答 `SnapshotVersion`，但同一版本号内导出集合仍可能不同），否则以后再往 v23 里加导出会重复同一个坑。

### P1-2 删除 AI 字幕包只校验"像包"，不校验"是它建的"

`Form设置_AI字幕.vb` 的删除流程：取文本框 `MTB_包目录` → `Ai字幕包.载入` 成功才继续 → 二次确认 → `Directory.Delete(目录, True)`。

`载入` 的判据是：目录存在 + `ai-subtitles.json` 版本 2/3 + worker 与模型文件体量合理（GGUF 还要 `llama-server.exe`）。**这判据只说明"这个目录里放着一个合法的包"，不能说明"这个目录是这个包独占的"**。真实数据丢失路径：

> 用户把包下载到已有的媒体目录（或后来把媒体文件放进包目录）→ 该目录仍然"载入成功" → 点"删除包" → 连同用户的媒体一起递归删除。

二次确认框会显示路径，但这只挡误点，不挡"我以为只删包"的合理误解。**修法**：包目录里写一个下载器自己生成的哨兵（如 `.3fp-package`，含创建时间/清单哈希），删除前要求哨兵在场；或删除前比对目录内容与清单，发现清单外文件就拒绝并列出。任一方案都能把"任意目录"收窄成"本程序建的目录"。

## 四、P2（应修或在正文说明）

### 4.1 直通接管时 AI 字幕必然静默无输出（产品交互缺口）

直通路径不解码，`AsrAudioTap` 拿不到 PCM；而且 `RecreateAudioRendererWithBitstream`（`PlayerSession.cpp:6049-6059`）**不像 `RecreateAudioRenderer` 那样把 `asrTap_`/`SetAudioRenderPlug` 迁到新渲染器**。结果是：直通打开时字幕界面仍显示"在跑"，但一段输出都没有，也没有任何提示。
建议：`EngagePassthrough` 在 `asrTap_` 非空且宿主要求字幕时拒绝接管（reason=`asr-tap-active`），或在宿主侧做互斥并在徽章上提示。至少要在正文写明"直通与 AI 字幕不可同时生效"。

### 4.2 下载器把"服务器不支持 Range"当致命错误

`Ai字幕包下载器.vb:435-442`：命中 404/416 时 `Continue For` 换源是对的；但服务器**忽略 Range 直接回 200 全量**时，代码算 `总长 = 响应.ContentLength + 已有` 必然与清单字节数不符，随后 `Return`（退出整个下载函数，不换源），提示"上游文件大小不符，更新下载清单"。真实成因是"这次没走续传"，不是"清单过期"，用户按提示做是白费。修法：识别 `StatusCode = 200 && 已有 > 0` → 废弃 `.part`、从头下载；只有 206 才按续传校验。

### 4.3 预取默认开、占用与进程模型未在正文交代

- 默认：`FFF3FP_PREFETCH` 缺省 **true**、helper 默认开、`mode` 默认 **2**、预算默认 **256 MB**；宿主侧图片按"当前 + 前后各 3 张"（≤7 条）下发，视频按"当前 + 前后各 1 条"（≤3 条）下发，并排除 RAW/`.dng/.raw/.yuv/.rgb`。
  `PrefetchService.cpp:673-695`；`前后预取控制器.vb:59-76`
- **注意：WARM 不看 flags。** helper 对计划里的**每一条**路径都先 `WARM`（单文件上限 `kMaxWarmBytes = 8 MiB`）再 `PROBE`（`PrefetchService.cpp:684-693`、`PrefetchHostMain.cpp:39,184-196`）。因此视频邻居同样会被 8 MiB 顺序预热，单次打开最多约 **3×8 = 24 MiB** 读；图片浏览最多约 **7×8 = 56 MiB** 读。
- **这是每个播放进程默认多一个后台进程 + 最多 256 MB 缓存 + 每次切换数十 MiB 顺序读的净新增行为**。机制上有 MemoryGuard 分档、Job 25% 单核硬上限（`PrefetchHostMain.cpp:101-117`）兜底，我认可，但"默认开"这个产品决定必须写进正文，否则评审看到的是"可选预取"。
- `CreateProcessW(..., bInheritHandles = TRUE, env = nullptr, cwd = directory)`：助手继承**进程内所有可继承句柄**。管道句柄确实是这么传给它的，但旁路的可继承句柄也一起漏出去。建议 `bInheritHandles` + `STARTUPINFOEX` 显式 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` 只白名单两个管道句柄。
- 助手路径 = 内核 DLL 同目录 `FFF.PrefetchHost.exe`，无签名校验。**风险等级可接受**（能写这个目录的人已经能替换内核 DLL），但正文应写明这条信任边界。
- `SetPlan` 的 64 KB 扫描：`cursor[length]` 在 `length == kScanLimit - consumed` 时会读到缓冲区第 65537 字节（1 字节越界读）。实际被 2048 路径上限挡住，建议顺手改成先判 `length < cap` 再取字符。

### 4.4 直通函数表"同 context 重装"会自毁

`AudioPassthroughLane::InstallTable` 在替换后销毁旧 context；若新表的 `context` 与旧表相同（同一模块重复钉同一张表），会把刚装上的 context 销毁。当前宿主用 `直通插槽已装` 挡住了重复安装，所以现在不可达，但这是 ABI 层的通用接口，建议加 `if (previous.context != api->context)` 再销毁。

### 4.5 直通 seek 过滤的帧时长公式单位错（低影响）

```cpp
// PlayerSession.cpp:6145-6146
av_rescale(frameSize, TicksPerSecond, max(1, linkSampleRate * 4 * 8))
```

`frameSize` 是字节，分母 `linkSampleRate × 4 × 8` 是"bits/s"量纲，多了一个 ×8。48k/2ch、1024 样本的帧算出来 2.7 ms，真实 21.3 ms。只在 `packet->duration <= 0` 且正在 seek 时生效，后果是最多少丢一个约 21 ms 的 burst（时钟随后由首个 burst 锚定），所以是 P3 级；但公式里那个 8 没有出处，建议删掉（2ch 应为 `linkSampleRate * 4`，通用式为 `linkSampleRate * linkChannels * 2`）。

### 4.6 CPU 放置诊断的无锁读

`FillDiagnosticSnapshot`（`PlacementPolicy.cpp:862-922`）在会话线程读 `tier0_`/`tier1_`/`workerThreadId_`/`processDefaultSetCount_`，写入方是 `OnPlaybackStart`/`ApplyTier`。函数注释已说明"不持有会话锁、不是同一瞬间的采样"，**但 `workerThreadId_` 是裸 `uint32_t`，读到撕裂值在形式上是 UB**（实际是单次对齐 32 位读，x86 不会撕裂）。建议改成 `std::atomic<uint32_t>`，成本为零。
