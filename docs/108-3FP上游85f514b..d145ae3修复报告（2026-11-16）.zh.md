## 2. 路线决策与理由（每条"为什么不选另一条路"）

| 路线 | 决定 | 为什么不选另一条路 |
|---|---|---|
| **JXL** | 诚实标注：`form=jhgm` + `verdict=fail_closed_unsupported` + `reason=jxl_gainmap_not_implemented`；删文档"已支持 JXL"表述 | 另一条路是真接 libjxl 解码：需要新增第三方依赖、OBU 解复用、JPEG XL 像素格式转换，成本不可控且本批红线不允许新依赖。"证伪即删声明"是唯一诚实解，比假装支持安全 |
| **PQ/HLG 底图 lift** | 一律 fail-closed（`IsHdrBaseRejected` 在 BMFF/JPEG 两路统一收口） | 另一条路是按 PQ/HLG transfer 正确反归一化后再施加 gain：需要把 base 的 PQ OETF 真正反变换到 linear 工作空间，而当前管线只有 sRGB→linear 一条路；硬上会产出像素错误的图。fail-closed 让用户看到"这张不支持"，而不是看到一张颜色错的图 |
| **grid/方向不匹配** | `decoded_not_applied`（解到了 gainmap 但不施加） | 另一条路是 `fail_closed_unsupported`：libavif 官方 grid 不匹配样本（`color_grid_*`、`seine_hdr_*`）本意就是"reader 能解 base、不应 lift"，归 unsupported 会把有效样本误判为能力缺失；归 applied 又会错 lift。`decoded_not_applied` 精确表达"base 已解、gain 未用" |
| **writer_version 未知 / tmap 尾随** | 返工第三轮裁定：canonical v0 解析成功但 trailing>0 → `fail_closed_unsupported`，reason=`tmap writer extension beyond canonical v0 layout (N trailing bytes) not implemented` | 另一条路是 consumed 截断后继续（F1 第一轮选择）：会把 `supported_gainmap_writer_version_with_extra_bytes.avif` 判成 `decoded_not_applied`，但该样本是 writer 私有扩展、reader 无权解释其语义；区分"能力不支持 writer 扩展"与"数据有效但不 lift"更准确。`trailingBytesIgnored` 计数仍保留作诊断 |
| **`family` 词表收紧** | 只允许 `{iso, apple, vendor128, none}`（`GainMapJpeg.h:38`）；JXL 不新增 `family=jxl`，WebP 不新增 `family=webp` | 另一条路是按容器类型扩词表：会让宿主 JSON schema 失配（宿主 `[JsonPropertyName]` 与 ABI pin 钉的是闭合枚举），且 `family` 的语义是"gainmap 元数据家族"而非"容器家族"，容器身份由 `form` 承载 |
| **AVIF 等长修复** | meta 内补 ISOBMFF `free` box 填差额；gap<8 时降级为 iloc body trailing zeros | 另一条路是扩 iloc extent 字段把字节塞回去：iloc 的 offset/length size 是 box header 写死的，改 size 需要重写 version/flags 并重新计算 baseOffset，改动面大且容易破坏 parser。`free` 是 ISO 14496-12 标准 no-op container，FFmpeg/合规 demuxer 直接跳过；gap<8 时连 free box 头都放不下，trailing zeros 对 iloc parser 不可见（按 extent_count 遍历） |
