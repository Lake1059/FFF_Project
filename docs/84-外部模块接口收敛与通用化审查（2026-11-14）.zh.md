## 0. 结论先行

### 0.1 一句话

**数据面已经基本通用化；真正专用的只剩控制面。**

模块自驱动泵已经在用内核的通用接口拉边数据、投 kind=3 色彩表、投辅层合成参数、读会话快照；宿主不再搬运载荷。今天仍带 `FFF_ColorTransform*` / `FFF_GetElCompositionApi` / `FFF_GetInjectionApi` 字样的部分，主要是**模块发现、授权、音频表提供、泵生命周期**这四类控制面接口，而不是数据面能力。

### 0.2 三类结论

| 类别 | 结论 | 代表接口 |
|---|---|---|
| **A. 可直接复用现有通用 ABI** | 不需要改内核，模块/宿主只需把表或载荷对齐到既有通用结构 | `FFF3FPAudioRenderPlug`、`FFF3FPAudioPassthroughApi`、`FFF3FPAuxiliaryComposition`、`FFF3FPDynamicMetadataPacket` kind=3、`FFF3FP_CopyFrameSideDataAfter`、`FFF3FP_CopyStreamSideData`、`FFF3FP_GetSnapshot`、`FFF3FP_GetPresentationCounter` |
| **B. 不能直接复用，但可改为非特定指向的中性 ABI** | 需要新增/改名一个通用模块信封，模块侧要实现；内核不需要新增数据面 ABI | 模块发现/清单、能力握手、授权、处理器 start/stop/status、模块显示名、激活提示 |
| **C. 应删除宿主绑定，或留在模块私有** | 宿主没有调用，删掉不改变行为；模块可保留旧导出做兼容 | `FFF_ColorTransformContentText`、`FFF_ColorTransformLastFramePeakNits`、`FFF_GetElCompositionApi`、`FFF_GetColorTransformApi` 的 `分析帧/复位/设置显示目标` 列、431 KB 载荷缓冲 |

### 0.3 最重要的量化事实

模块当前有 **10 个宿主可见导出**、**5 张能力表**。宿主真正还在用的只有 **7 个导出**：

- 授权状态
- 状态文本（只用于握手失败日志）
- 解锁
- 音频渲染表
- 音频直通表
- 注入泵表
- 色彩变换表（只作为“模块在且版本对”的 gate）

另外 **3 个导出已经是死绑定**：

- `FFF_ColorTransformContentText`
- `FFF_ColorTransformLastFramePeakNits`
- `FFF_GetElCompositionApi`

色彩变换表的 4 个功能列——`变换版本`、`分析帧`、`复位`、`设置显示目标`——宿主 **一个都没有真正调用**。其中 `分析帧` 和 `复位` 只在握手校验里被要求“非空”，`变换版本` 只喂给一个从不被读取的 `布局版本` 字段，`设置显示目标` 的方法没有调用者。

这不是“模块接口设计得不好”，而是**宿主已经从“宿主泵”切换到“模块自驱动泵”后，旧 ABI 没有跟着收掉**。收敛的第一收益不是改名，而是删掉这些已经不再承载行为的宿主绑定。

模块表镜像：`色彩变换能力表`（`色彩变换模块接口.vb:251-262`），x64 布局为：


| 列 | 宿主使用方式 | 真实行为 | 判断 |
|---|---|---|---|
| `大小` | 握手校验、旧表归一 | 只用于信封 | 保留 |
| `版本` | 握手校验 | 只用于信封 | 保留 |

## 2. 数据面：已经可以复用通用接口

这一节回答“哪些可以复用已有通用接口”。结论是：**数据面的目标接口全部已经存在，且不需要改内核。**

### 2.1 音频渲染：表结构逐字段相同

模块导出 `FFF_GetAudioRenderApi` 返回的 56 B 表：

```text
size, version, context, name, supports, render, reset, destroy
```

内核的 `FFF3FPAudioRenderPlug`（`FFF.Player.AudioRenderPlug.h:71-97`）是同一组字段、同一顺序、同一 56 B 布局。宿主当前也是把整张表钉住后交给 `FFF3FP_SetAudioRenderPlug`（`播放器会话.vb:724`），内核在装载点复制表，`context` 所有权转移。

**可复用程度：100%。**
唯一“专用”的是获取这张表的导出名 `FFF_GetAudioRenderApi`，不是表本身。把提供方式换成通用 capability getter 后，宿主安装插槽的代码可以原样保留。

### 2.2 音频直通：表结构逐字段相同

模块导出 `FFF_GetAudioPassthroughApi` 返回的 48 B 表：

```text
size, version, context, describe, pack, reset, destroy
```

内核的 `FFF3FPAudioPassthroughApi`（`FFF.Player.AudioPassthrough.h:63-86`）逐字段相同，宿主也是整表交给 `FFF3FP_SetAudioPassthroughApi`（`播放器会话.vb:825`）。

**可复用程度：100%。**
同上，专用的是 `FFF_GetAudioPassthroughApi` 这个名字，不是表。

### 2.3 辅层合成：内核 API 可复用，但模块输出布局还没对齐

内核的 `FFF3FPAuxiliaryComposition`（`FFF.Player.Api.h:1913-1929`）是 32 B：

```text
size(4) + version(4) + frameIndex(8)
+ enabled(4) + residualCenter(4) + residualShift(4) + maxValue(4) = 32 B
```

模块的 `原生合成参数`（`色彩变换模块接口.vb:335-344`）也是 32 B，但字段是：

```text
enabled, disableResidual, baseBitDepth, enhancementBitDepth,
videoBitDepth, residualCenter, residualShift, maxValue
```

两者**同宽但不同序**，而且模块输出没有 `frameIndex`。宿主现在靠 `分析增强层` 取参数，再由 `设置辅层合成` 手工映射到内核结构（`播放器原生接口.vb:1290-1308`）。这不是“直接复用”，是“手工翻译”。

**可复用程度：内核侧 100%，模块侧需要一次输出布局对齐。**
两条可行路线：

1. **模块自驱动路线（推荐）**：模块泵本来就有内核会话句柄，直接在模块内部调 `FFF3FP_SetAuxiliaryComposition`。宿主不再解析 `FFF_GetElCompositionApi`，也不用 `原生合成参数`。模块内部保留自己的 8 字段分析结构，只在调用内核前映射为 5 字段请求。
2. **宿主转交路线**：模块把输出改成 `FFF3FPAuxiliaryComposition` 本体（带 `frameIndex`），宿主原样转交，不再手工映射。这样 `FFF_GetElCompositionApi` 可退化成通用 “auxiliary request” capability。

无论哪条，**内核的 `FFF3FP_SetAuxiliaryComposition` 不需要改**。

### 2.4 色彩变换载荷：kind=3 已经是通用数据面

内核的通用动态元数据通道（`FFF.Player.Api.h:1484-1636`）已经定义了：

- `FFF3FPDynamicMetadataPacket`，40 B
- `FFF3FPDynamicMetadataKind::ExternalColorTransform = 3`
- `FFF3FPColorTransformPayload`，431,296 B，内容为 `lutDomain + 3x3 matrix + 33^3 LUT`
- `FFF3FP_SetDynamicMetadata` 整表替换
- `FFF3FP_ClearDynamicMetadata` 按 kind 清表
- 帧号匹配规则与 HDR10+ 注入共用

模块的 `色彩变换输出`（32 B）是：

```text
size, kind, kindVersion, payloadSize, payload, capacity, reserved
```

它不是 `FFF3FPDynamicMetadataPacket` 本体（后者多 `frameIndex` 和 `version` 语义），但它承载的 **payload 就是 `FFF3FPColorTransformPayload`**。模块自驱动泵在内部把它组装成 packet，再调 `FFF3FP_SetDynamicMetadata`；宿主不再持有 packet 镜像。

**可复用程度：payload 100%，wrapper 不需要进宿主。**
如果将来要做宿主驱动的通用分析器，模块应直接输出 `FFF3FPDynamicMetadataPacket`，而不是再定义一套 `色彩变换输出`。当前自驱动模式下，宿主连 wrapper 都不需要。

### 2.5 帧边数据 / 流级边数据：模块已经直接拉内核

内核已经提供两个纯字节接口：

- `FFF3FP_CopyFrameSideDataAfter`（`FFF.Player.Api.h:1784-1824`）
- `FFF3FP_CopyStreamSideData`（`FFF.Player.Api.h:1825-1872`）

两者都只传 `sideDataType` 号码和字节，内核不解释内容。模块泵拿到内核句柄后自己解析这些导出、自己拉帧边数据和流级配置记录；宿主的 `色彩变换输入`（56 B，含 `元数据/元数据大小/配置记录/配置记录大小`）在当前路径中已经没有调用者。

**可复用程度：100%。**
宿主的 `色彩变换输入` 结构可以删；模块侧继续用内核两个 Copy 导出即可。

### 2.6 显示目标 / 峰值 / 呈现计数：快照已经够用

内核 `FFF3FPSnapshot` 已有：

- `displayPeakNits`
- `displayFullFramePeakNits`
- `effectiveTargetPeakNits`
- `sourcePeakNits`
- `frameIndex`
- `presentedVideoFrames`

模块泵本来就用 `FFF3FP_GetSnapshot` 和 `FFF3FP_GetPresentationCounter` 判回退、追帧、取当前帧号。宿主再维护一个 `设置显示目标` 回调没有意义：模块自己就能从快照读显示目标。

**可复用程度：100%。**
如果模块确实需要宿主显式告诉它一个“本次会话显示目标”，那也应该作为通用分析输入的一个字段（例如 `displayPeakNits`），而不是模块专用的 `setDisplayTarget` 函数指针。

### 2.7 数据面复用总结

| 能力 | 现有通用 ABI | 是否逐字节相同 | 宿主是否已用 | 收敛动作 |
|---|---|---|---|---|
| 音频床渲染 | `FFF3FPAudioRenderPlug` | 是（56 B） | 是 | 只换提供方式 |
| 音频直通 | `FFF3FPAudioPassthroughApi` | 是（48 B） | 是 | 只换提供方式 |
| 辅层合成 | `FFF3FPAuxiliaryComposition` | 内核 32 B；模块参数 32 B 但不同序 | 内核 API 已用，模块参数手工映射 | 模块泵直调内核，或模块输出改成内核结构 |
| 色彩变换 | `FFF3FPDynamicMetadataPacket` kind=3 + `FFF3FPColorTransformPayload` | payload 相同；wrapper 不同 | 模块泵已用 | 宿主删 wrapper / 缓冲 |
| 帧边数据 | `FFF3FP_CopyFrameSideDataAfter` | 纯字节 | 模块泵已用 | 宿主删输入结构 |
| 流级配置 | `FFF3FP_CopyStreamSideData` | 纯字节 | 模块泵已用 | 宿主删输入结构 |
| 显示目标/峰值 | `FFF3FPSnapshot` | 字段已有 | 模块泵已用 | 删 `setDisplayTarget` |
| 呈现计数 | `FFF3FP_GetPresentationCounter` | 纯计数 | 模块泵已用 | 不动 |

**这一节的核心判断：数据面没有“需要新增通用 ABI”的项。** 所有目标接口都已经存在；剩下的是模块侧愿不愿意把输出对齐到既有结构。

## 3. 控制面：不能直接复用，需要中性化

这一节回答“哪些可以改为非特定指向的接口”。控制面没有现成通用 ABI，但有明确的收敛方向。

### 3.1 模块发现与身份：从“固定文件名”改为“清单 + 描述符”

当前宿主代码里写死了：

- `模块文件名 = "FFF.HDRdp.Test.dll"`（`色彩变换模块接口.vb:33`）
- `FC_COLORTRANSFORM_DIR`（`:485`）
- 搜索序：环境变量 → 真实 exe 目录 → `AppContext.BaseDirectory` → 裸文件名（`:429-480`）

这些是**特定指向**：文件名、环境变量名、搜索策略都在宿主源码里。它们不应该继续作为主路径。

建议：

```text
Modules\<module-id>\module.json
{
  "schema": 1,
  "entry": "FFF.HDRdp.Test.dll",
  "abi": 1,
  "capabilities": ["authorization", "audio-render", "audio-passthrough", "processor"],
  "requires": ["frame-side-data-ring", "dynamic-metadata-injection"],
  "activation": "optional"
}
```

宿主只读 `entry`、`abi`、`capabilities`、`requires` 这些**通用字段**；具体文件名是数据，不是编译进代码的常量。环境变量改为通用的 `FFF3FP_MODULE_DIR`，旧 `FC_COLORTRANSFORM_DIR` 只留在兼容适配器里。

这样做的收益：

- 本体不再知道模块叫什么、属于哪个格式；
- 同一套加载器可以加载未来的其他外部模块；
- 发布护栏可以继续用旧商标文件名做 denylist，但不需要在正常加载路径里复述它。

### 3.2 能力握手：从 5 个 `FFF_Get*` 改为 1 个 `GetCapability`

当前模块用 5 个独立导出提供 5 张表：

```text
FFF_GetColorTransformApi
FFF_GetAudioRenderApi
FFF_GetAudioPassthroughApi
FFF_GetElCompositionApi
FFF_GetInjectionApi
```

这是典型的“每加一种能力就加一个导出名”。宿主每加一种能力就要改 `GetProcAddress` 列表，模块也要加一个裸导出。

建议一个中性信封：

```c
#define FFF3FP_EXTERNAL_MODULE_ABI 1u

enum FFF3FPExternalCapability : uint32_t {
    Authorization      = 1,
    AudioRender        = 2,
    AudioPassthrough   = 3,
    Processor          = 4,
    ColorAnalysis      = 5,  // 可选，宿主驱动模式才需要
};

struct FFF3FPExternalModuleDescriptor {
    uint32_t size;
    uint32_t version;
    const char* id;             // 稳定、 opaque，例如 "com.example.hdr"
    const char* displayName;    // 宿主可显示；可为空
    uint32_t capabilities;      // 位掩码
    uint32_t requirements;      // 需要内核哪些通用导出
    uint32_t flags;             // requiresActivation / singleton 等
};

struct FFF3FPExternalModuleApi {
    uint32_t size;
    uint32_t version;
    void* context;
    int32_t (*getDescriptor)(void* context, FFF3FPExternalModuleDescriptor* out);
    int32_t (*getCapability)(void* context, uint32_t capability,
                             uint32_t version, void** outTable);
};

extern "C" __declspec(dllexport)
int32_t FFF3FP_ExternalModuleGetApi(uint32_t abiVersion,
                                   FFF3FPExternalModuleApi* out);
```

`getCapability` 返回的表：

- `AudioRender` → `FFF3FPAudioRenderPlug*`（既有类型）
- `AudioPassthrough` → `FFF3FPAudioPassthroughApi*`（既有类型）
- `Authorization` → 新的 `FFF3FPExternalAuthApi`
- `Processor` → 新的 `FFF3FPExternalProcessorApi`
- `ColorAnalysis` → 可选的新 `FFF3FPExternalColorAnalysisApi`

这样宿主只认识一个入口和一组 capability ID；模块加能力只需要加一个 ID，不需要加新的裸导出名。

### 3.3 授权：不能复用内核 ColorExtension 桩，建议新增 per-module auth

内核的四个 ColorExtension 导出（`FFF.Player.Api.h:934-941`）已经在 `PlayerApi.cpp:53-76` 永久惰性化：

- `FFF3FP_GetColorExtensionStatus()` 恒 0
- `FFF3FP_GetColorExtensionStatusText()` 恒 nullptr
- `FFF3FP_SetColorExtensionAuthorizationPrompt()` 丢弃回调
- `FFF3FP_AuthenticateColorExtension()` 恒 `NotSupported`

它们还有两个不适合直接复用的问题：

1. **进程级、无模块参数**：一个进程只能有一个“color extension”授权态，和当前模块的进程级单例同病。
2. **语义已废弃**：这些符号的历史含义是旧私有模块，现有宿主也把它们当 deprecated 镜像；复活它们会把“absent”语义破坏掉。

因此不建议“把模块授权改成调内核 ColorExtension”。建议新增一个 per-module 的通用授权表：

```c
enum FFF3FPExternalAuthState : uint32_t {
    Unavailable = 0,
    Locked      = 1,
    Ready       = 2,
};

enum FFF3FPExternalAuthText : uint32_t {
    Explanation         = 1,
    PromptLabel         = 2,
    PersistenceFailure  = 3,
};

enum FFF3FPExternalAuthResult : uint32_t {
    Rejected             = 0,
    Accepted             = 1,
    AcceptedNotPersisted = 2,
};

struct FFF3FPExternalAuthApi {
    uint32_t size;
    uint32_t version;
    void* context;
    int32_t (*getState)(void* context);
    const char* (*getText)(void* context, uint32_t purpose);
    int32_t (*submit)(void* context, const char* credentialUtf8);
};
```

这几乎就是模块现有授权面的中性版：

- 状态值 1/2 不变；
- 文本用途 1/2/3 不变；
- 提交结果 0/1/2 不变；
- 去掉 `ColorTransform` 前缀和模块专属票据语义。

宿主只看到 `Locked/Ready`、`Accepted/AcceptedNotPersisted`，不再知道票据落在 `exe 旁` 还是 `%LOCALAPPDATA%\FFF.HDRdp.Test`。票据路径、码校验、落盘策略全部留在模块内部。

### 3.4 自驱动处理器：从 `InjectionApi` 改为通用 Processor

当前 `FFF_GetInjectionApi` 的 32 B 表是：

```text
size, version, start, stop, readStatus
```

`readStatus` 填 184 B 的 `FFFInjectionStatus`：

```text
size, running, injectedFrames, unchangedFrames, skippedFrames,
unattributedFrames, lastFrameIndex, lastPeakNits,
contentText[64], compositionText[64]
```

这套语义本身已经接近通用，问题只在名字和单例：

- “Injection” 是特定指向的词；
- start/stop 没有 context，导致模块泵是进程级单例，宿主必须维护 `_泵当前句柄` 的跨会话归属；
- 184 B 状态里 `contentText` / `compositionText` 是模块措辞，宿主只显示，不应解释。

建议：

```c
struct FFF3FPExternalProcessorStatus {
    uint32_t size;
    uint32_t version;
    uint32_t running;
    uint64_t processedFrames;
    uint64_t unchangedFrames;
    uint64_t skippedFrames;
    uint64_t unattributedFrames;
    int64_t  lastFrameIndex;
    float    lastPeakNits;
    char     statusText[64];
    char     detailText[64];
};

struct FFF3FPExternalProcessorApi {
    uint32_t size;
    uint32_t version;
    void* context;
    int32_t (*start)(void* context, FFF3FPHandle session);
    void (*stop)(void* context);
    void (*getStatus)(void* context, FFF3FPExternalProcessorStatus* out);
};
```

字段数与 184 B 状态一一对应，只把 `injected` 改成 `processed`、`contentText` 改成 `statusText`、`compositionText` 改成 `detailText`。`context` 让模块可以选择：

- 支持多实例（每个会话一份泵）；
- 或者声明 `singleton`，由宿主串行化。

不管哪种，宿主不再需要“模块是进程级单例”的隐含知识。

**重要边界**：这只是把控制面中性化，不改变“泵在模块内部”的架构。不要因为改了 ABI 就把逐帧循环搬回宿主；那会重新引入宿主搬运载荷、宿主追环、宿主判回退的旧问题。

### 3.5 显示文本 / 峰值 / 激活 UI

当前宿主有三条显示通道：

1. 模块 `注入状态.内容文本字节` → `色彩变换内容描述` → HDR 行“内容：”
2. 模块 `注入状态.末帧峰值尼特` → `色彩变换外部峰值尼特` → HDR 行“模块峰值”
3. 模块 `注入状态.合成文本字节` → `色彩变换合成文本` → HDR 行附加段

这三条已经由 184 B 状态统一提供，**不需要**再解析 `FFF_ColorTransformContentText` / `FFF_ColorTransformLastFramePeakNits`。后者是旧宿主泵时代的线程局部快照，和 184 B 状态不是同一拍；宿主现在读状态，反而更连贯。

激活 UI 仍然写死“色彩变换模块”：

- `Form1.vb:749`：“检测到色彩变换模块，但尚未解锁。”
- `Form1.vb:757`：标题“色彩变换模块解锁”
- `Form1.vb:767/780`：“色彩变换模块已解锁。”

这可以中性化为：

```text
检测到可选扩展模块「{displayName}」，需要激活。
```

`displayName` 来自 descriptor；为空时回退“可选扩展模块”。宿主不需要知道它是色彩变换、音频还是别的能力。

### 3.6 不能复用、也不建议硬改的部分

| 项 | 为什么不能直接复用 | 建议 |
|---|---|---|
| 内核 ColorExtension 四个导出 | 永久惰性桩、进程级、无模块参数、历史语义已废弃 | 不复活；用 per-module auth |
| 模块自有授权票据/码校验 | 属于模块私有授权逻辑，宿主不应解释 | 只暴露 `AuthApi` 的中性结果 |
| 模块内部 `transformVersion` / `analyzeFrame` / `reset` | 宿主不再调用；模块泵内部自用 | 从宿主绑定删掉；模块可保留旧导出 |
| 模块内部 `ElComposition` 的位深/残差字段 | 内核 `FFF3FPAuxiliaryComposition` 只需要 5 个通用字段 | 模块内部映射；不要把这些字段塞进本体 |
| 模块进程级泵单例 | 是当前 ABI 无 context 的结果 | 新 Processor API 加 context；或显式声明 singleton |

## 5. 实现层面的硬问题（比命名更优先）

这一节是“反复分析”得到的具体问题，不是风格建议。

### 5.1 旧 32 B 表：注释说兼容，代码实际拒绝（不存在越界读）

`尝试装载` 的注释（`色彩变换模块接口.vb:662-666`）说：

> 旧模块的 32 B 表不含尾列：40 B 镜像的 PtrToStructure 会把表外的堆内存读进尾列 —— 按 size 归一，缺列读作零指针。

但下一段校验（`:668-670`）是：

```vb
If 入口返回 <> 0 OrElse 表.版本 <> 表版本 OrElse
   表.大小 < CUInt(Marshal.SizeOf(Of 色彩变换能力表)()) OrElse
   表.分析帧 = IntPtr.Zero OrElse 表.复位 = IntPtr.Zero Then
```

`Marshal.SizeOf(色彩变换能力表)` 是 40。因此：

1. 宿主分配的是 40 B 托管表，`New 色彩变换能力表` 会把所有字段零初始化；旧模块只写前 32 B，尾部 8 B 仍是宿主自己的零区。**所以当前这条路径不构成越界读**——注释里“读进表外的堆内存”说法不准确。
2. 真正的问题是：`表.大小` 被旧模块写成 32，归一化把 `设置显示目标` 置零后，下一行 `表.大小 < 40` 仍然命中，整表被拒。

也就是说，注释承诺的“旧表归一”在代码里没有发生。旧 32 B 模块会被拒绝，但不是被越界读打死的。这是一个**兼容性断言与实现不一致**的硬问题。

> 注意：如果将来把“模块填调用方缓冲”改成“模块返回自己的 32 B 静态表指针”，再用 40 B `PtrToStructure`，那才会真的越界。当前实现不是那种形状。

修复方向：

- 先只读 `size/version`（8 B）的信封，确认 `size`；
- `size >= 40` 才读完整 40 B 表；
- `size == 32` 时用 32 B 结构读，`setDisplayTarget` 直接置零；
- 如果要兼容 v2 模块，握手失败后可回退用版本 2 再试一次；如果明确不支持旧件，则删掉“旧表归一”的注释，不要保留假兼容。

### 5.2 握手强制要求宿主不调用的指针

`:668-670` 要求 `分析帧` 和 `复位` 非空，但这两个指针在宿主侧没有真实调用。后果：

- 一个只提供 `Processor` / `AudioRender` / `AudioPassthrough` 的新模块，即使能力完整，也会被握手拒绝；
- 模块为了过门，必须继续导出两个宿主永远不调的旧函数；
- 接口收敛被“假依赖”锁死。

修复方向：

- 握手只要求 `size/version`，以及“至少一个宿主真正要用的能力”；
- `分析帧/复位` 改为可选，不再作为 `尝试装载` 的前置条件；
- 如果要保留旧模块兼容，旧表列可以读，但不参与接受/拒绝判断。

### 5.3 431 KB pinned buffer 是纯浪费

`尝试装载` 在 `:713-714` 分配并 pin：

```vb
Dim 载荷缓冲区 = New Byte(CInt(载荷容量) - 1) {}
载荷句柄 = GCHandle.Alloc(载荷缓冲区, GCHandleType.Pinned)
```

这个缓冲只被 `分析帧()` 使用（`:922`），而 `分析帧()` 没有调用者。模块自驱动泵有自己的缓冲。结果是每个会话白拿 **431,296 B** 的 pinned 大对象，外加一个 GCHandle。

修复方向：

- 删除 `载荷缓冲区` / `载荷句柄` / `取载荷副本` / `载荷容量` 常量；
- 删除 `色彩变换输出` 结构和 `分析帧` 方法；
- 如果将来要恢复宿主驱动分析，再按需分配，而不是每个会话常驻。

### 5.4 音频表“已交出”标志与真实所有权不同步

`尝试取音频渲染表` 在 `:1229` 设置 `_音频表已交出 = True`，但此时表还没有交给内核；内核可能拒绝（`播放器会话.vb:724-730`）。`尝试取音频直通表` 同样在 `:1291` 设置 `_直通表已交出 = True`，也在内核接受之前。

后果：

- 内核拒绝时，模块仍被认为“已交出”，`Dispose` 不会 `FreeLibrary`，形成安全但永久的映射泄漏；
- 反之，`Dispose` 只检查 `_音频表已交出`（`:1312`），不检查 `_直通表已交出`；当前 `播放器会话.释放` 会先撤直通表（`:1287`），所以正常路径不踩空，但这个不变量依赖调用顺序，后续改动很容易破。

修复方向：

- 把“表已创建”和“所有权已转移”分开；
- 宿主在 `FFF3FP_SetAudioRenderPlug` / `FFF3FP_SetAudioPassthroughApi` 返回成功后，显式调用 `标记已交出`;
- 内核拒绝时调用模块的 `destroy` 归还 context（直通侧当前未做，见 `播放器会话.vb:825-833`）；
- `Dispose` 用 `_任何裸表已交出` 或两个标志的并集，避免依赖调用顺序。

### 5.5 本体源码仍持有大量专用常量与结构

即使不看运行时行为，宿主源码里仍有：

- `FFF.HDRdp.Test.dll`（`:33`）
- `FC_COLORTRANSFORM_DIR`（`:485`）
- `FFF_ColorTransform*` 六个导出名（`:36-53`）
- `FFF_GetElCompositionApi`（`:88`）
- `FFF_GetInjectionApi`（`:99`）
- `%LOCALAPPDATA%\FFF.HDRdp.Test` 票据路径注释（`Form1.vb:669`）
- `FFF.DolbyVision.Test.dll` + `FFF.HDRdp.Test.dll` 发布护栏（`FFF.Player.vbproj:341`）
- `原生色彩变换载荷` 431 KB 镜像（`播放器原生接口.vb:759-775`）
- ColorExtension deprecated DllImport（`播放器原生接口.vb:731-749`）

这些不全是“运行时接口”，但它们是本体对某个具体模块的**源码级指向**。收敛的目标不是把字符串藏起来，而是让主路径不再需要它们；旧名只出现在一个可删除的 legacy adapter 里。

### 5.6 优先级

| 优先级 | 项 | 理由 |
|---|---|---|
| **P0** | 32 B 表归一后仍被拒 | 兼容性断言与实现矛盾；旧件实际不可用 |
| **P0** | 握手强制要求 `分析帧/复位` | 直接阻断中性模块 |
| **P1** | 431 KB pinned buffer | 每会话纯浪费，且让宿主继续镜像私有载荷 |
| **P1** | 音频表所有权标志 | 内核拒绝时泄漏；Dispose 依赖调用顺序 |
| **P1** | 宿主删除 3 个死导出 | 减少专用面和误判 |
| **P2** | 模块文件名/环境变量/UI 文案 | 需配合清单/descriptor，属于中性化 |
| **P2** | ColorExtension deprecated 镜像 | 纯死代码，删除即可 |

## 6. 推荐的收敛路径

### Phase 1：不改模块二进制，先删宿主死面（低风险）

目标：不动模块 ABI，只把宿主不再使用的东西删掉，并修正握手/旧表问题。

1. 删除 `FFF_ColorTransformContentText` / `FFF_ColorTransformLastFramePeakNits` 的解析、委托、方法。
2. 删除 `FFF_GetElCompositionApi` 的解析、`合成能力表`、`原生合成参数`、`分析增强层`、`支持增强层合成`。
3. 删除 `分析帧`、`复位`、`设置显示目标尼特`、`取载荷副本`、`可用`、`布局版本`，以及 431 KB 载荷缓冲。
4. 删除 `播放器原生接口.原生色彩变换载荷` / `色彩变换载荷尺寸` / ColorExtension deprecated DllImport。
5. 握手改为只校验 `size/version`，不再要求 `分析帧/复位` 非空；`设置显示目标` 不再作为接受条件。
6. 旧 32 B 表改为 size-first 读取，确保只读模块实际写入的部分；如果保留 v2 兼容，加版本回退。
7. 音频表所有权：成功后标记“已交出”，拒绝时归还 context；`Dispose` 检查所有已交出表的并集。
8. 把 `FFF.HDRdp.Test.dll` / `FC_COLORTRANSFORM_DIR` / `FFF_ColorTransform*` 移到单独的 `LegacyColorModuleAdapter.vb`，主加载器不再引用。

Phase 1 的验收标准：

- 模块缺席、旧件、未解锁、表不合格时行为与今天一致（静默降级）；
- 模块在场且已解锁时，音频渲染/直通/注入泵行为不变；
- 现有回归测试通过；
- 源码中主路径不再出现专用文件名/导出名（只允许 legacy adapter 出现）。

### Phase 2：新增中性模块信封，模块侧迁移

目标：用一个通用入口替代 5 个 `FFF_Get*`，用通用 auth/processor 替代专用授权/注入表。

1. 定义 `FFF3FP_ExternalModuleGetApi` + descriptor + `getCapability`。
2. 定义 `FFF3FPExternalAuthApi`、`FFF3FPExternalProcessorApi`。
3. 音频能力继续返回既有 `FFF3FPAudioRenderPlug` / `FFF3FPAudioPassthroughApi`，不复制结构。
4. 模块实现新入口；旧 `FFF_Get*` 保留为兼容别名，至少保留一个发布周期。
5. 宿主优先走新入口；找不到时回退 legacy adapter。
6. 激活 UI 用 descriptor `displayName`，不再写死“色彩变换模块”。

Phase 2 的验收标准：

- 同一份宿主可以加载两个不同 module id 的测试模块；
- 不依赖固定文件名/固定导出名；
- 旧模块仍能通过 legacy adapter 工作；
- 新模块只提供 `Processor + AudioRender` 时也能被接受，不因缺少 `分析帧/复位` 被拒。

### Phase 3（可选，不建议现在做）：宿主驱动通用分析器

如果将来需要：

- 多模块并行分析；
- 宿主统一调度、统一错误恢复；
- 模块不允许自己开线程；

才考虑 `FFF3FPExternalColorAnalysisApi`，由宿主拉边数据、调模块 `analyze`、再投 `FFF3FP_SetDynamicMetadata`。

现在不建议做，因为：

- 当前模块自驱动泵已经把线程、游标、回退探测封装在模块内；
- 宿主重新引入泵会恢复旧的载荷搬运、追环、回退判断复杂度；
- 数据面已经通用，收益不足以抵消风险。

- 旧商标 denylist 只出现在发布脚本/工程文件，不出现在运行时加载路径。

## 8. 最终建议

1. **先做 Phase 1，不要先改模块 ABI。** 宿主侧有一大批死绑定和 431 KB 死缓冲，删掉它们不会改变现网行为，却能立刻缩小专用面。
2. **不要复活内核 ColorExtension 四个桩。** 它们是进程级、永久 absent 的历史符号；复用一个“不能工作”的接口只会把问题藏得更深。
3. **数据面继续用 `FFF3FP_*`，不要新增内核 ABI。** 音频表、辅层合成、kind=3 payload、边数据、快照、呈现计数都已经够用。
4. **控制面用一个通用模块信封替代 5 个 `FFF_Get*`。** 这是“非特定指向”的核心；模块文件名、导出名、授权文案都从代码移到清单/descriptor。
5. **保留 legacy adapter，但只保留一个发布周期。** 旧模块还能用，主路径已经中性；等模块迁移完成，删掉 adapter 和旧名。
6. **不要因为中性化把自驱动泵搬回宿主。** 当前架构的正确之处是“模块自己追帧、宿主只 start/stop”；中性化只改控制面名字和生命周期，不改这个分工。
