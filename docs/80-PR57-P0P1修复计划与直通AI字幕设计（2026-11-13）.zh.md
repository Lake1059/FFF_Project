## 1. 事实基线（截至 196f63a，行号可能漂移，以函数名/内容为准）

1. **tap 的唯一生产点**是 PCM 渲染路径：`WasapiRenderer.cpp:731-736`
   ```cpp
   // ASR tap: the raw decoded bed, ahead of any bed route, fold-down, resample
   if (auto* tap = asrTap_.get()) tap->Produce(frame, position100ns);
   ```
2. **直通接管重建渲染器时不迁移 tap**：`RecreateAudioRendererWithBitstream`（`PlayerSession.cpp:6042-6078`）只 `reset + make_unique + SetBitstreamFormat + Start`，对比 `RecreateAudioRenderer` 在 `:2196-2204` 会 `SetAsrTap` 迁移。重建后新渲染器 `asrTap_ == nullptr`。
3. **直通全程不解码**：`HandlePassthroughPacket`（`:6080-6172`）只做 parser 归一化 → `ptLane_.Pack` → `EnqueueBitstream`。
4. **`audioDecoder_` 在直通里既没用也没被释放**：`EngagePassthrough`（`:5948-6005`）没有 `avcodec_free_context`，但 `:6130` 与 `:4424` 的注释都写着「engagement releases this decoder（release-then-own）」。注释与实现不一致——这是 P2-A 要注意的既有事实，不是本文新引入的。
5. **tap 环是单生产者/单消费者、drop-oldest、不阻塞**：`AsrAudioTap.h:13-26,60-77`；`Produce` 支持任意 ≤24 声道、任意 `AVSampleFormat`（`AsrAudioTap.cpp:77-137`）。
6. **宿主 tap 生命周期**：`播放器AI字幕控制器.尝试启动` 在媒体打开后 `启用音频Tap(句柄, 0)`（`:308`），`停止` 里 `停用音频Tap`（`:264`）；内核侧 `EnableAudioTap` 用 worker 命令把 tap 装到渲染器（`PlayerSession.cpp:2878-2883`），`DisableAudioTap` 同样在 worker 上摘（`:2895-2897`）。
7. **AI 字幕开关现状**（该子系统在 base `72af915` 已存在，不是本 PR 新增——已用 `git ls-tree` 核对；本 PR 只新增 `Ai字幕包下载器.vb`）：

## 2. P0-1 全量修复：IEC 61937 端点块对齐

### 2.1 根因

`WasapiRenderer.cpp:1248-1252`：

```cpp
exclusiveCandidate.Format.wBitsPerSample = 16;
exclusiveCandidate.Format.nBlockAlign =
    static_cast<WORD>(4 * exclusiveCandidate.Format.nChannels);
exclusiveCandidate.Format.nAvgBytesPerSec =
    decided.linkSampleRate * exclusiveCandidate.Format.nBlockAlign;
```

契约写明 burst 是 **s16le**（`FFF.Player.AudioPassthrough.h:73`「emit at most one burst (s16le ready)」），`wBitsPerSample = 16` 也说明每样本 2 字节。于是：

| linkChannels | 正确 blockAlign（2×ch） | 现值（4×ch） | `nAvgBytesPerSec` 偏差 |
|---|---|---|---|
| 2（AC3/EAC3/DTS 2ch 载体） | 4 | 8 | 2× |
| 8（TrueHD/DTS-HD HBR 载体） | 16 | 32 | 2× |

后果二选一：端点 `IsFormatSupported` 直接拒（**直通永不生效**，`:1271-1275` 置 `bitstreamFormatRejected_` 后回退解码），或端点容忍但按 2× 字节率消耗载体（接收端锁不住、时钟锚点错）。

### 2.2 改动（唯一必要改动）

```cpp
// IEC 61937 carrier: 16-bit words on the wire, so a link frame is
// 2 bytes per channel (4 for the 2ch carrier, 16 for the 8ch HBR
// carrier). 4*nChannels described 32-bit samples and made every
// burst meter at twice its real byte cost.
exclusiveCandidate.Format.nBlockAlign =
    static_cast<WORD>(2 * exclusiveCandidate.Format.nChannels);
```

`nAvgBytesPerSec` 保持 `linkSampleRate * nBlockAlign`（自动正确）。

### 2.3 连带修复（无需改代码，但要写进验收）

`outputBlockAlign_ = activeFormat->nBlockAlign`（`:1379-1380`）是下面全部计量的唯一来源，公式修正后**自动**正确：

| 位置 | 用途 | 修正前 |
|---|---|---|
| `:1074` `Buffered100ns` | `bitstreamQueuedBytes_ / outputBlockAlign_` → 队列时长 | 队列深度报一半（8 字节当成一帧） |
| `:1584-1586` | 每次 `GetBuffer` 可拷字节 / 实际帧数 | 把 8 字节当成链路一帧；端点按 48 kHz 每帧消耗 8 字节，等于以 **2×** 速率吃掉 burst |
| `:1664-1665` | `submittedBytes = renderedFrames * outputBlockAlign_` + 零填充 | 字节数与设备缓冲自洽，但「帧」被定义成 8 字节：同样一缓冲只覆盖一半的音频时长 |
| `:1639` | `bitstreamQueuedBytes_ -= copied` | 与上一条同源，队列按 2× 速率被清空 → 生产跟不上，underrun |

也就是说 P0 不是「音质问题」，是「直通要么不工作、要么以 2× 速率消耗载体（队列被抽空后 underrun）」——**它同时解释了 PR 正文「已实测直通」缺少正向路径**。

### 2.4 注释同步修正

- `:1069-1071`「s16 words, so 4 bytes per frame per channel pair」：4 字节是 **2ch 一帧**的总字节数，不是「每声道对」；8ch 一帧是 16 字节。改为「2 bytes per channel」。
- `:1580-1583`「outputBlockAlign_/outputSampleRate_ already speak link units」：修正公式后才成立，补一句依赖 `nBlockAlign = 2*nChannels`。

### 2.5 诊断（建议随 B1 一起加，便于实机判定）

在 bitstream 端点打开成功后打一行日志（沿用 `Emit` 或 `OutputDebugString`）：

```
pt-endpoint: bits=16 blockAlign=4 avg=192000 linkRate=48000 linkCh=2 burst=6144 mask=0x3F
```

判定「容忍型驱动」：修复前这行会显示 `blockAlign=8`，但端点仍 SUCCESS；修复后变 `4` 且播放正常。

### 2.6 验收

| 场景 | 通过标准 |
|---|---|
| AC3 2ch → 直通 | `audioPassthroughActive=1`；blockAlign=4；`Buffered100ns` 稳定在设备缓冲量级；`underruns` 不增长 |
| TrueHD 7.1 → 直通 | blockAlign=16；`ptBurstsRendered` 持续增长；声音正常、无爆音 |
| 同一机器修复前后对比 | 修复前「端点拒绝 / 2× 速率吃掉 burst」二者之一；修复后必须转为正常播放 |
| 模块拒绝 / 端点独占冲突 | `FallBackFromPassthrough` 仍按原路径回退，PCM 正常 |

> 局限：本文没有实机数据。`IsFormatSupported` 在具体驱动上是「拒」还是「容忍」，只有作者侧用上面那行日志才能定论；两种情况的修法是同一个。

### 2.7 回滚

单行 revert，无状态迁移。

## 3. P1-1 全量修复：附加导出改为可选解析

### 3.1 爆炸半径（复述关键链路）

- `播放器原生接口.vb:1695-1734` 的 5 个导出是静态 `DllImport`：`SetAudioBinauralPolicy` / `GetAudioBinauralStatus` / `SetAudioPassthroughApi` / `SetAudioPassthroughMode` / `GetAudioPassthroughState`。
- 同文件其余附加导出走 `解析可选导出`（`:609-614`，`NativeLibrary.TryGetExport` → `Marshal.GetDelegateForFunctionPointer`），缺失时返回 `Nothing`。
- `SnapshotVersion` 从第一笔提交 `5d88c1b` 就是 23；`SetAudioBinauralPolicy` 到第 6 笔 `cb1ba13` 才加 → **存在「版本 23 但缺这些导出」的内核**，可达。
- 真正被引爆的点是 `播放器会话.vb:820`（在 `安装音频直通插槽核心` 内）：
  ```vb
  Try
      检查结果(播放器原生接口.FFF3FP_SetAudioPassthroughMode(取得句柄(), 音频直通模式偏好))
      Dim 结果 = 播放器原生接口.FFF3FP_SetAudioPassthroughApi(取得句柄(), 钉住.AddrOfPinnedObject())

  Finally
      钉住.Free()

  ```
  这里**没有** `Catch ex As EntryPointNotFoundException`。异常向上冒到 `启动色彩变换通路` 的 blanket catch（`:260-261`）或 `唤醒色彩变换通路` 的（`:309-311`），于是同一 Try 块里排在后面的

## 4. P1-2 全量修复：包目录归属与删除安全

### 4.1 三条危险路径

1. **删除**：`Form设置_AI字幕.vb:263-291` 只要求 `Ai字幕包.载入` 成功。用户把一个官方包下到 `D:\Media\某电影\`（该目录里还有视频/字幕），点「删除包」→ `Directory.Delete(目录, True)` → 整个媒体目录没了。
2. **下载**：`下载目标目录()` 直接返回 `MTB_包目录.Text`；`下载包Async` 在 `:282` 取 `Path.GetFullPath` 后就开始往里写，只在「文件已存在且字节数相符」时跳过（`:311-319`）——**不判断目录是否为空、是否属于本程序**。于是「下到已有目录」与「删除」组合成完整的数据丢失路径。
3. **不可恢复**：`Directory.Delete` 不进回收站（大目录也不适合进）。

### 4.2 方案：归属哨兵 + 双向校验

**哨兵文件**：包根下 `.3fp-package.json`

```json
{"owner":"FFF.Player/AI字幕","version":1,"manifest":"ai-subtitles.json","createdUtc":"2026-11-13T00:00:00Z"}
```

## 5. P2-A：直通下额外一路解码 PCM 给 AI 字幕（内核）

### 5.1 为什么现在必然静默

```
媒体打开 → 宿主装 tap（EnableAudioTap → 渲染器 SetAsrTap）
        → 首个完整音频帧 → EngagePassthrough
        → audioRenderer_.reset() + 新建 bitstream 渲染器（不迁移 tap）
        → 之后每个包只 Pack + EnqueueBitstream，不解码
        → 环里永远没有块 → 宿主 pump 读到 Empty → 字幕无字
```

三个独立原因叠加：**tap 装在旧渲染器上被一起销毁**、**直通路径没有 `Produce` 调用**、**没有 PCM 可喂**。只修其中任何一个都不够。

### 5.2 方案比较

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 复用 `audioDecoder_` 内联解码** | 直通时每个 AU 也送进现成的 `audioDecoder_`，只 `Produce` 给 tap，不交给渲染器 | 零新上下文、零新生命周期；`DoSeek` 已经 flush 它（`:8221`）；**回退时解码器是热的**——不会重新等 TrueHD/DTS-HD 的下一个 major sync；内存不增 | 与播放解码器耦合；`:4424` / `:6130` 的「engage 会释放解码器」注释必须改正；EOF 的 `DrainInternalAudio` 需要保证影子侧已排空（本方案每包都排空，见 §5.3.3） | **推荐** |
| B. 独立影子解码器 | tap 装且 lane engaged 时新建专用 `AVCodecContext` | 与播放路径完全隔离；可把播放解码器释放掉 | 多一套生命周期（7 个接线点 + open/flush/release）；回退时重开的是**冷**解码器，TrueHD 要等下一次 major sync 才能稳定出帧 | 备选（仅在要求彻底隔离时） |
| C. 让模块解码 | 模块契约只收已编码帧，不解码 | — | 越界，违反 ABI | 不可行 |

选 A 的关键理由不是「代码少」，而是**回退路径**：直通因端点/模块原因回退到 PCM 时，A 的解码器一直在按顺序吃同一批 AU，状态是连续的；B 的 `FallBackFromPassthrough` 会新建解码器（`:6029-6033`），TrueHD 这类带 major sync 的码流在同步点之前会连续报错，而 `internalAudioDecodeErrorCount_` 是有限额的。

### 5.3 方案 A 的实现

#### 5.3.1 新增成员（`PlayerSession.h`，与 `asrTap_` 放同一区）

```cpp
// worker 线程上的 tap 裸指针。安装/摘除都在 Enqueue 的 worker 命令里完成，
// Produce 也只在 worker 上发生——与渲染器 asrTap_ 的既有不变量相同
// （WasapiRenderer.h:344-348），所以这里不需要锁。
AsrAudioTap* asrTapWorkerRaw_ = nullptr;
int asrShadowErrors_ = 0;        // 连续解码失败计数
bool asrShadowDisabled_ = false; // 解不了这类流：本次 tap 生命周期内不再尝试
```

不新增解码器、不新增帧缓冲：复用 `audioDecoder_`（`PlayerSession.h:577`）与 `audioDecodeFrame_`（`:578`），以及一个复用的 `AVPacket` 成员（或用栈上 `AVPacket`，见下）。

#### 5.3.2 接线点（只有 3 处需要动）

| 接线点 | 动作 | 线程 |
|---|---|---|
| `EnableAudioTap` 的 worker 命令（`:2878-2883`） | **在 `std::move(installed)` 之前** `asrTapWorkerRaw_ = installed.get()`（渲染器那份引用继续持有对象）；`asrShadowErrors_ = 0; asrShadowDisabled_ = false;` | worker |
| `DisableAudioTap` 的 worker 命令（`:2895-2897`） | `asrTapWorkerRaw_ = nullptr` | worker |
| `HandlePassthroughPacket` 尾部（`:6164-6170` 之后） | `if (asrTapWorkerRaw_) FeedAsrShadow(...)` | worker |

不需要额外处理的四处（写清楚是为了防止实现时画蛇添足）：

- **`EngagePassthrough`**：`audioDecoder_` 本来就开着（`DoOpen` 的 `:4419` 打开，engage 没有释放），`DoSeek` 也会 flush 它；不新建、不迁移。
- **`DoSeek`**：`:8221` 已 `avcodec_flush_buffers(audioDecoder_)`；tap 代次已由 `NoteTapGeneration()`（`:8268`）盖戳。
- **`FallBackFromPassthrough`**：解码器非空 → 不会重建（`:6029`），继续用同一个热态解码器，正是 A 的优势。
- **`DoClose`**：`:8848` 已 `avcodec_free_context(&audioDecoder_)`。

调用点：

```cpp
if (burstSize > 0 && audioRenderer_ != nullptr) {
    ++snapshot_.decodedAudioFrames;
    (void)audioRenderer_->EnqueueBitstream(ptBurstBuffer_.data(), burstSize,
        burstPts, burstDuration);
}
// 影子解码只喂 tap，不碰渲染器；放在入队之后，避免解码耗时压在突发排队前面。
if (asrTapWorkerRaw_ != nullptr)
    FeedAsrShadow(frameData, static_cast<std::uint32_t>(frameSize), position100ns);
return true;
```

> 线程约束是这个方案能不加锁的前提：`EnableAudioTap`/`DisableAudioTap` 的 lambda 都在 `Enqueue` 里跑，`HandlePassthroughPacket` 本来就在 worker 上；`DoClose` 由 `Close()` 的 `Enqueue` 进入（`:1485`）。不要让任何一处跑到别的线程。

#### 5.3.3 喂数

```cpp
void PlayerSession::FeedAsrShadow(const std::uint8_t* data, std::uint32_t size,
    std::int64_t position100ns) noexcept {
    if (audioDecoder_ == nullptr || asrTapWorkerRaw_ == nullptr || asrShadowDisabled_) return;
    AVPacket pkt{};
    pkt.data = const_cast<std::uint8_t*>(data);
    pkt.size = static_cast<int>(size);
    pkt.pts = AV_NOPTS_VALUE;   // 位置用外部 position，不依赖 packet pts
    // send_packet 对非引用计数的 data 会自行拷贝，parser 的输出缓冲可以复用。
    const auto send = avcodec_send_packet(audioDecoder_, &pkt);
    if (send < 0 && send != AVERROR(EAGAIN)) {
        // TrueHD/DTS-HD 在流中途打开时要等下一个 major sync，之前每帧都会报错；
        // 阈值必须足够宽（约数秒的 AU），否则「从中间续播」会误判成解不了。
        if (++asrShadowErrors_ > 200) asrShadowDisabled_ = true;
        return;
    }
    if (audioDecodeFrame_ == nullptr && (audioDecodeFrame_ = av_frame_alloc()) == nullptr) return;
    while (true) {
        const auto recv = avcodec_receive_frame(audioDecoder_, audioDecodeFrame_);
        if (recv == AVERROR(EAGAIN) || recv == AVERROR_EOF) break;
        if (recv < 0) { if (++asrShadowErrors_ > 200) asrShadowDisabled_ = true; break; }
        std::int64_t pos = position100ns;
        if (audioDecodeFrame_->best_effort_timestamp != AV_NOPTS_VALUE) {
            const auto mapped = StreamTimestampPosition100ns(
                format_, audioStream_, audioDecodeFrame_->best_effort_timestamp);
            if (mapped != AV_NOPTS_VALUE) pos = mapped + audioDelay100ns_;
        }
        asrTapWorkerRaw_->Produce(audioDecodeFrame_, pos);
        av_frame_unref(audioDecodeFrame_);
        asrShadowErrors_ = 0;
    }
}
```

要点：

- **每包排空**：`receive_frame` 循环跑到 `EAGAIN`，保证 `DrainInternalAudio`（`:1289-1291`）在 EOF 时没有残留帧可解码——这是复用 `audioDecoder_` 的前提，也是不破坏 bitstream 渲染器的关键。
- **不重采样、不下混、不折降**：`AsrAudioTap::Produce` 原样搬 `AVSampleFormat` 与声道布局（`AsrAudioTap.cpp:77-137`），worker 自己处理。直通下解码器输出可能是 7.1 `fltp`，24 声道上限内。
- **不复用 `DecodePacket`**：那条路径会走 `QueueAudioFrame` → 渲染器，直通下会把 PCM 塞进 bitstream 端点。这里直接 `send/receive`，只 `Produce`。
- **时间戳**：优先 `frame->best_effort_timestamp` → `StreamTimestampPosition100ns + audioDelay100ns_`，回退本次 AU 的 `position100ns`。ASR 窗口是秒级，一帧的锚点误差无感。
- **失败策略**：连续 200 次解码错误（约数秒的 AU，覆盖 TrueHD/DTS-HD 从流中途打开时的「等 major sync」窗口）→ `asrShadowDisabled_ = true`，本次 tap 生命周期内不再尝试；直通播放**完全不受影响**。任何一次成功收帧都会把计数清零，所以正常播放中偶发的单帧错误不会累积。用户关开一次 AI 字幕（重装 tap）即可重置这个标志。
- **队列**：不新增队列。worker 内联，tap 环 drop-oldest 兜底（`AsrAudioTap.h:23-26`）。

#### 5.3.4 改正两条过时注释（不写这条，后来的人会把解码器当成漏释放）

`:4424` 与 `:6130` 都写着「engagement releases this decoder（release-then-own）」，但 `EngagePassthrough`（`:5948-6005`）**从未释放** `audioDecoder_`。在方案 A 下这不是 bug，而是设计的一部分：解码器要一直留着当影子解码源，同时让回退无缝。两条注释改成事实：

```cpp
// The FFmpeg decoder STAYS open for the whole passthrough track: it is the
// ASR shadow decode source when a tap is installed (see FeedAsrShadow), and
// keeping it warm makes FallBackFromPassthrough seamless -- a decoder opened
// from scratch mid-stream would have to wait for the codec's next sync point.
// With no tap installed it is simply idle.
```

如果要改成「engage 真释放」，就必须同时选方案 B 并为回退准备冷启动策略（预读/重同步），收益不抵复杂度——**不做**。

### 5.4 代价

| 项 | 量级 | 说明 |
|---|---|---|
| CPU | AC3/EAC3 约 1%；DTS 约 1–2%；TrueHD 7.1 约 5–10% 单核（**待实测**） | 只在 tap 已装（AI 字幕开）时付出 |
| 内存 | **零新增**（复用既有 `audioDecoder_` / `audioDecodeFrame_`） | tap 环的 32 MiB 才是大头，且本来就存在 |
| 音频抖动 | 解码在 burst 入队之后；单帧通常 <3 ms，burst 银行 ≥61440 B（2ch/48k 约 0.32 s） | 需在低配机 + TrueHD 上测 underrun |

若实测 TrueHD 在弱机上出现 underrun，退化顺序：① 影子解码降到半帧率（每 2 个 AU 解 1 个，ASR 仍可用）；② 把影子解码移到独立线程 + 8 包队列（独立上下文，回到方案 B 的线程化形态）；③ 直通 + AI 字幕提示「二选一」。

### 5.5 失败可见性（宿主侧）

tap 已装、直通生效，但连续 5 s `blocksProduced == 0` → `播放器AI字幕控制器` 记一次日志 + 一次操作提示：

> 「当前为源码直通模式，AI 字幕拿不到 PCM（内核未启用直通解码），字幕已暂停。」

判定素材现成：`读取音频直通状态`（`:856-876`）的 `生效` + `取音频Tap统计`（`:217`）。

### 5.6 验收

| 场景 | 通过标准 |
|---|---|
| TrueHD 7.1 + 直通 + AI 开 | `blocksProduced` 持续增长；`blocksDropped=0`；字幕出字；`underruns` 不增长 |
| 同上，关 AI | tap 被摘 → `blocksProduced` 停止；`audioDecoder_` 不再被喂（它本来就开着，无内存回落可观测） |
| 播放中开 / 关 AI | 开关后 1 s 内开始 / 停止出字，无需重新打开媒体 |
| seek | `generation` 变化；无 seek 前文本残留；`blocksProduced` 继续 |
| 端点切换 / 直通回退 | `FallBackFromPassthrough` 复用同一个热解码器 → 渲染器重建并迁移 tap → PCM 路径接管 → 字幕不断 |
| 模块拒绝直通 | 从未 `MarkEngaged`，`FeedAsrShadow` 不执行，AI 字幕照常（PCM 路径） |
| 老内核（无 tap） | `支持音频Tap=false` → AI 项不可用，直通正常 |

## 6. P2-B：AI 字幕的「可用开关」与「在既有字幕机制中手动选择」

### 6.1 现状的真实问题

不是「没有开关」，而是**开关语义错了、入口太隐蔽、状态不可见**：

| 事实 | 后果 |
|---|---|
| `设置.vb:154 Ai字幕已停用 = False` | 「未停用」= 默认启用 |
| `应用设置` 只要包有效且未停用就 `尝试启动`（`:152-156`） | **选到有效包即自动启用**，用户没有「我要开」的动作 |
| 设置页没有启用/停用控件 | 唯一入口是标题栏菜单的一棵子树 |
| 流选择器字幕段只有 关闭 / 内嵌 / 外挂（`播放器流选择器.vb:83-108`） | 用户按「选字幕」的直觉找不到 AI |
| AI 与普通字幕可同时绘制（`Form1.vb:539-544`） | 两套字幕叠加，没有「当前字幕源」概念 |
| `Form1.vb:54` 注释「默认关」 | 与实现相反，误导后来的人 |

### 6.2 目标语义（推荐）

**AI 字幕是一种字幕来源，与「关闭 / 内嵌 / 外挂」并列互斥。**

- 状态唯一：`设置.Ai字幕已停用`（内部负向键，界面一律显示为「启用」；默认值改为 `True`，见 §6.4.1）。
- 三处入口同一状态源：
  1. **流选择器**（主入口，用户找字幕的地方）：字幕段新增「AI 实时字幕（实时生成）」。
  2. **标题栏菜单**（快捷入口，保留）：`启用 AI 实时字幕` 勾选态读同一状态。
  3. **设置页**（可发现性）：AI 字幕页顶部一个开关 + 一行状态（包 / 内核 tap / 直通解码）。
- 包只决定「可用」：选包、换包、删包都不改变 `启用`；只影响该项是否可点、菜单是否置灰。
- 互斥：选 AI → `关闭字幕()` 再启用；选任何其它字幕项或「关闭字幕」→ 停用 AI。

### 6.3 为什么不把 AI 做成真正的 `外部字幕轨道`

`外部字幕轨道`（`外部字幕自动加载器.vb:6-37`）是**静态生成器模型**：SRT/SUP/ASS 生成器 + 文件路径 + 流索引 + 租约（`尝试进入使用` / `离开使用` / `已请求释放`）。AI 字幕是**滚动增量 cue**，没有稳定条目表，也没有可预先读取的总时长；硬塞进去要改生成器接口、租约释放、帧缓存三条语义。用「伪项 + 既有绘制扩展层」拿到同样的 UI 语义，改动面小一个数量级。

### 6.4 改法（按文件）

#### 6.4.1 `设置.vb`（必须兼容存量）

```vb
' 现值（base 就有，不要改名）：Public Property Ai字幕已停用 As Boolean = False
' 改为默认 True，并在注释里写清"缺键=新装=关"的语义：
Public Property Ai字幕已停用 As Boolean = True
```

为什么不是新增 `Ai字幕启用` 正向键：`Ai字幕已停用` 在 base 已存在，改名会让所有存量设置文件里的旧值失效（`System.Text.Json` 会把缺失属性留成字段初始值），等于强行把老用户的选择抹掉。改默认值的语义正好合适：

- **新装**（无设置文件 / 无该键）→ 初始值 `True` → 停用 → **默认关**，符合「不该在选个目录后就自动起子进程」。
- **存量**（文件里写着 `false`）→ 反序列化覆盖初始值 → 未停用 → 保持原来的自动启用行为，不惊动老用户。
- 界面上统一用正向措辞（「启用 AI 实时字幕」），内部继续存负向键，二者用 `Not` 转换。

`规范化()` 不需要新增分支。

#### 6.4.2 `播放器AI字幕控制器.vb`

```vb
' 可用 = 包有效 + 内核有 tap（P2-A 落地后不再受直通影响）
Friend ReadOnly Property 可用 As Boolean
    Get
        Return 包 IsNot Nothing AndAlso 播放器原生接口.支持音频Tap AndAlso Not 已释放
    End Get
End Property

''' 给标题栏菜单 / 流选择器 / 设置页状态行用的人话原因；可用时返回空串。
Friend ReadOnly Property 不可用原因 As String
    Get
        If 已释放 Then Return "已释放"
        If 包 Is Nothing Then Return "未安装扩展包"
        If Not 播放器原生接口.支持音频Tap Then Return "内核不支持音频采集"
        Return String.Empty
    End Get
End Property

' 启用 = 可用 + 用户显式打开（内部仍存负向键）
Friend ReadOnly Property 启用 As Boolean
    Get
        Return 可用 AndAlso Not 设置.实例对象.Ai字幕已停用 AndAlso Not 已释放
    End Get
End Property

''' 统一入口：菜单、流选择器、设置页都走这里。
Friend Sub 设置启用(值 As Boolean, Optional 提示 As Boolean = True)
    If 已释放 Then Return
    If 值 AndAlso Not 可用 Then
```

## 10. 需要拍板的四件事（默认按推荐执行）

1. **默认开还是默认关**：推荐「新装默认关、存量不惊动」——`Ai字幕已停用` 默认值改 `True`，存量文件里的 `false` 仍按原样。理由：一个会起子进程、吃 CPU、拉 1 GB 模型的特性不应该在「选个目录」之后自动运行；但也不该在升级时把已经开着的人悄悄关掉。
2. **AI 与普通字幕互斥还是并存**：推荐互斥。理由：现有叠加会同时画两层；AI 自带双语，能覆盖「原文+译文」；并存可作为后续选项，不改状态模型。
3. **TrueHD 影子解码 CPU 是否接受**：推荐接受并实测；若弱机 underrun，按 §5.4 退化，而不是取消功能。
4. **手动放置的包是否允许「删除包」**：推荐拒绝（无哨兵即拒绝）。理由：程序无法证明目录归属时不应替用户删数据。

### 13.2 与计划的偏差（有意为之）

1. **互斥下沉到了 `播放器控制器`，不是流选择器四委托。** 原方案（§6.4.3）想在每个字幕项的点击处理器里调「AI 停用」，但这样标题栏菜单的开关就成了第三条不受控的路径；而且流选择器比 AI 控制器先构造，四委托必须全部延迟判空。改由 `播放器控制器` 持有 `AI字幕` 引用，在 `关闭字幕/选择内嵌字幕/选择外挂字幕` 三处统一停 AI，AI 启用路径通过 `清除普通字幕` 反向清普通字幕——两条边都只有一处实现。`关闭字幕(保留AI字幕:=True)` 就是给这条反向边用的。
2. **设置页没有加第三个开关。** AI 字幕现在的身份是「字幕来源第四项」，主入口在字幕列表，快捷入口在标题栏菜单；设置页再加一个 checkbox 等于第三份状态显示，且 `Form设置_AI字幕.Designer.vb` 是固定坐标 + `Dock=Top` 手排布局，加行要重排十余个 Panel，收益不抵回归风险。需要时可在设置页调用同一个 `作为字幕源启用/停用`，不必改状态模型。
3. **没有引入 `可用` 独立属性。** 原设计（§6.4.2）想区分「可用（包有效 + 内核有 tap）」与「启用（用户打开）」。实际沿用 `启用 = 包 IsNot Nothing AndAlso Not 停用`；内核 `支持音频Tap` 缺失由 `尝试启动` 记日志并跳过（既有行为）。字幕列表只在 `有可用包` 时摆出该项，已经达到「选包只决定可用」的语义。
4. **§5.5 的「直通 5 秒无 block」宿主提示未实现。** 影子解码失败只会静默（内核 `asrShadowDisabled_`）或写日志，不会主动告诉用户。作为后续增强，入口在 `播放器AI字幕控制器.采样诊断`（每 5 秒读一次 `已产块数`，配合 `GetAudioPassthroughState.生效` 即可判定）。
5. **P1-2 的兼容取舍已按计划执行**：目录里已有文件但没有哨兵时，下载会被拒绝（提示换空目录）；手动放置的旧包也不能用「删除包」按钮，只能手动删。这是「宁可拒绝，不替用户删数据」的代价。
6. **`AI字幕菜单.vb` 一字未改**：它的勾选读 `控制器.启用`，`切换启用` 已改走新的统一入口，菜单自动跟随。

### 13.5 已知残余风险

- `FeedAsrShadow` 对 `avcodec_send_packet` 的 `EAGAIN` 只跳过该 AU（每包都排空，正常不会触发）；若出现会丢一帧 ASR 输入，不影响播放。
- TrueHD/DTS-HD 从流中途打开时，影子解码在 major sync 前会连续报错；阈值 200 AU（约数秒）后才禁用。**seek 会清零并重新允许尝试**，但若新位置仍无 major sync，会再次禁用——续播场景下可能整段没有 AI 字幕，但直通音频正常。
- 影子解码与渲染入队同线程；TrueHD 在弱机上是否 underrun 仍需实测（§5.4 的退化顺序未实现）。
- P0 公式改动后某些驱动可能从「容忍」变成「拒绝」；端点日志与既有 `bitstreamFormatRejected_` 回退可立即定位。

## 14. 本体/模块显示分割与全量测试（2026-11-13 续，按“模块注入”改向）

### 14.1 边界规则（本轮修正后的硬约束）

- **模块 → 内核**：`FFF3FPAudioPassthroughFormat.displayName` 是模块拥有的静态 UTF-8 文本；lane 只把它当**不透明显示串**复制，不解释格式语义。codecId / flags / subFormat / linkRate / linkChannels / burstBytes 仍只走数值。
- **内核 → 宿主**：`DeviceChanged` 带 `displayName`；`FFF3FP_GetAudioPassthroughState` 的 `name` 输出同样回模块显示名。模块缺席或没给名字时为空。
- **宿主 → UI**：宿主只做承载，模块激活时把它的文本作为**额外段/额外行**追加，不替换宿主基础段，也不因为模块有文本就把宿主段抹掉。直通行 `直通：<模块显示名>`（模块没给名字时报中性“已接管”）；HDR 行保留基础规格，模块内容追加为 `内容：<模块文本>`；动态段、宿主源峰值照常保留，模块逐帧峰值作为额外段；残差合成段用模块自己的措辞。**宿主不自造格式身份名，也不做编解码枚举回退**。
- **本体源码**：显示路径里不再有格式身份名；直通相关注释统一改成“标准码流”这类中性工程词。模块名/规格词只存在于运行时注入的内存里，不编译进宿主。
- **打包**：既有 `RejectPrivateColorExtensionPublish` 继续拒绝旧商标私有 DLL `FFF.DolbyVision.Test.dll`；中性模块文件名 `FFF.HDRdp.Test.dll` 可发布。

### 14.4 残余边界

- `FFF3FPAudioPassthroughFormat.displayName` 是**模块注入通道**，不是宿主自包含内容：宿主二进制没有它的字面值，只有模块运行时传入的指针/字符串副本；模块缺席时直通行不出现，模块接管但没给名字时只显示中性“已接管”。
- 基础 HDR 规格（`HDR10 PQ` / `HDR HLG` 等）仍由宿主按源元数据判定并保留；模块文本只作为 `内容：` 额外段出现，不替换、不覆盖基础规格。
- 名称经 `读取音频直通状态` 复制到 256 字节缓冲，超长会被截断——这是既有导出契约，模块应自控显示名长度。
- 媒体本身的编解码标签（`DTS`/`TRUEHD` 等）仍会作为**片源信息**出现在文件关联、流选择器、信息图层里；这是格式识别，不是模块显示。若要求连这些格式名也全部从本体移除，需要另开一轮口径决策。
- 解锁对话框的“色彩变换模块解锁”是宿主自有描述，不含模块品牌/厂商名，保留。
