# Intel NPU 可行性测试报告（第三方实测，2026-10-29）

> **归档说明**：正文由第三方在 Intel Core Ultra 9 285H（Arc 140T iGPU + AI Boost NPU、
> OpenVINO 2026.4.1）上实测，原始文件 `D:\迅雷下载\NPU可行性测试报告.md`。
> 归档时**正文一个字没改**，下面只记录 3FP 侧怎么采信它。
>
> **采信的三条**（与我们的实现一致，被独立复现）：
>
> 1. NPU 能跑 `conv_frontend`，rel_err ≈ 0.001（我们的 `--verify` 阈值 0.02）。
> 2. int8 的 encoder / decoder 必须留 CPU（NPU 只吃 fp32）。
> 3. iGPU 强于 NPU（5.4~5.9× vs 1.5~1.9×，且 iGPU 支持动态形状）⇒ 有 Arc 的机器
>    优先 `ov-gpu`，与 `qwen3_ort.AUTO_ORDER` 一致。
>
> **不采信的一条**：§2.1 把失败归因成「NPU 不支持动态形状、必须静态」。报错原文是
> `Upper bounds are not specified` —— 拒的是**上界 INT64_MAX**，不是"维度会变"。
> 我们用带界 reshape `[1, 1..3200, 128]`，**一次编译覆盖全部帧数**（离线 NPU4000
> 已验 500 / 3000 / `[1, 1..3000]` 三种）。所以 §4.5 那套「预定义帧数集合 + 形状路由
> + padding/trimming」**不要照做**：trimming 真丢音频、padding 到离散档会改 mel
> 内容，是拿精度去换一个我们本就不存在的问题。
>
> **最大的空洞**：只测了 conv 单段，没测端到端。conv 每窗只跑一次前向（毫秒级），
> 而我们的端到端是秒级（`OvBackend` pad30=False 实测 rtf 0.96）—— **conv 只占链路
> 约 1%**。所以 1.5~1.9× 是**段级**加速比，不能写成"字幕快一倍"。NPU 这条腿当前的
> 结论是「能用、省电」，不是「更快」。

## 二、NPU 测试结果

### 2.1 动态形状编译

**结果：失败**

NPU 插件不支持动态形状编译。尝试以动态形状编译 conv_frontend.onnx 时，OpenVINO NPU 后端在 Pad 算子处触发 LLVM 硬崩溃：

```
[ERROR] Upper bounds are not specified for node 'ShapeOf_16025'
[ERROR] Only constant input is supported for pad
LLVM ERROR: Failed to infer result type(s)
```

此错误导致进程直接崩溃（退出码 127），无法进入后续的静态形状回退逻辑。

**根因**：Intel NPU 编译器（vpux-compiler）要求所有张量维度在编译期完全确定，不支持动态形状（`?`维度）。模型中的 Pad 算子输入含有符号维度，NPU 后端无法处理。

### 2.2 静态形状编译

**结果：通过**

绕过动态形状、直接以静态形状 (1, N, 128) 编译后，NPU 成功执行推理。

## 四、可行性结论

### 4.1 NPU 是否可用？

**结论：有条件可用。**

| 维度 | 判定 | 说明 |
|------|------|------|
| 硬件识别 | **通过** | OpenVINO 正确枚举 NPU（Intel AI Boost） |
| 模型编译 | **有条件通过** | 必须使用静态形状，动态形状会导致编译器崩溃 |
| 数值正确性 | **通过** | 相对误差 0.1%，远低于 2% 阈值，无 NaN |
| 推理性能 | **通过** | 比 CPU 快 1.5x ~ 1.9x |
| 工程可用性 | **需要适配** | 需对模型做静态形状 reshape 后才能送上 NPU |

### 4.2 关键限制

1. **不支持动态形状**：NPU 编译器要求所有维度在编译期固定。Qwen3-ASR 的 conv_frontend 输入形状为 `[batch, frames, 128]`，其中 `frames` 维度随音频长度变化。每次遇到新长度都需要重新编译（0.6 ~ 1.2 秒），对实时场景有影响。

2. **编译开销**：首次编译耗时 0.6 ~ 1.2 秒。如果音频长度种类有限（如固定 1s / 5s / 10s / 30s），可以预编译缓存，后续直接加载。

3. **性能不及 iGPU**：NPU 加速比约 1.5x ~ 1.9x（vs CPU），而 iGPU 可达 5x ~ 6x。NPU 的优势在于功耗更低，适合持续推理场景。

### 4.3 推荐方案

针对 Qwen3-ASR 在 Intel Core Ultra 平台上的部署，建议按优先级选择：

| 优先级 | 方案 | conv_frontend 设备 | 说明 |
|--------|------|-------------------|------|
| 1 | **iGPU 加速** | GPU.0 (Arc 140T) | 动态形状原生支持，5x+ 加速，无额外适配 |
| 2 | **NPU 加速** | NPU (AI Boost) | 需预定义帧数集合、静态形状预编译；功耗更优 |
| 3 | **纯 CPU** | CPU | 无兼容性问题，20ms 级延迟可接受 |

### 4.4 NPU 适用场景

NPU 路线在以下场景有独特价值：

- **功耗敏感场景**：NPU 的能效比优于 GPU，适合电池供电的持续推理
- **GPU 已被占用**：当 iGPU/dGPU 需要跑其他任务时，NPU 可作为独立加速器
- **固定长度音频**：如对讲机、固定时长语音片段，帧数可预定义，静态形状编译开销可摊薄

### 4.5 实施建议

若选择 NPU 路线，需要：

1. **预定义帧数集合**：根据业务场景确定常见的音频长度（如 1s=100帧、5s=500帧、10s=1000帧、30s=3000帧）
2. **预编译缓存**：启动时一次性编译所有目标形状，缓存 CompiledModel
3. **形状路由**：推理时根据实际音频长度选择最近的预编译形状，或做 padding/trimming
4. **conv 段专用**：仅将 fp32 的 conv_frontend 送上 NPU，int8 的 encoder/decoder 留 CPU（这是 Qwen3-ASR 的架构约束）

## 五、总结

| 问题 | 回答 |
|------|------|
| NPU 硬件是否可用？ | **是**，Intel AI Boost 被 OpenVINO 正确识别 |
| conv_frontend 能否在 NPU 上运行？ | **能**，但必须使用静态形状 |
| 计算结果是否正确？ | **是**，相对误差 0.1%，无 NaN |
| NPU 是否比 CPU 快？ | **是**，1.5x ~ 1.9x 加速 |
| NPU 是最佳选择吗？ | **不一定**，iGPU 加速比更高（5x+）且支持动态形状 |
| 推荐方案 | 优先 iGPU；NPU 适合功耗敏感或 GPU 被占用的场景 |

**最终结论：Intel NPU 可以运行 Qwen3-ASR 的 conv_frontend 段，数值正确且有加速效果，但需要静态形状适配。在同时拥有 Arc iGPU 的平台上，iGPU 是更省心的选择；NPU 的价值在于低功耗独立加速。**
