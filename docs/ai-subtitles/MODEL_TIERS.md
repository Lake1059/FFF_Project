# 模型档位：低性能设备的回退方案

- 日期：2026-10-23
- 适用：AI 字幕（Qwen3-ASR-0.6B，llama.cpp 后端）
- 相关：`PACK_FORMAT.md`（清单 `models` 字段）、`BACKEND_MATRIX.md`（后端选型）

---

## 1. 为什么需要"档位"而不是"换包"

Qwen3-ASR 家族最小就是 0.6B，没有更小的同族模型；能省的只有**量化位数**。

但"换包"对普通用户成本太高：包目录、清单、python、二进制全都要重配一遍，
而且换回标准档又要再配一遍。所以做成**同一个包带多档权重**，设置里换档即可：

```
设置 → AI 字幕 → 高级选项 → 模型档位：[默认档（清单 model 字段）| Q8_0 | Q4_K_M]
```

换档是**启动期参数**：改完 worker 会重启（约 10 s），播放不受影响。

---

## 2. 三档的实测数据

| 档位 | 主权重 | 投影 | 磁盘合计 | 载入显存¹ | 相对速度 | 精度 |
| --- | --- | --- | --- | --- | --- | --- |
| **Q8_0**（默认） | 768 MiB | 204 MiB | ~972 MiB | 1991 MiB | 1.0× | 基准 |
| **Q6_K** | 594 MiB | 204 MiB | ~798 MiB | 1642 MiB | ~1.1× | 与 Q8_0 无可测差异 |
| **Q4_K_M**（低配） | 456 MiB | 204 MiB | ~660 MiB | 见注² | CUDA 实测 rtf 0.14–0.15 | 英文 WER 2.11% → 2.26%³ |

¹ 显存增量 = `llama-server` 进程占用量，实测于本机（CUDA 后端，窗口 5 s）。
² Q4_K_M 由本机 `llama-quantize` 从 bf16 现场量化得到（456.11 MiB / 5.09 BPW，19 s）。
  显存**没有取得可与 Q6_K/Q8_0 对比的稳态值**：`nvidia-smi` 增量只有 333–381 MiB，
  因为权重走 mmap、按需上传，和当初 Q8_0 的 1991 MiB 不是同一口径，不能拿来比。
³ 第三方数据：`myflow-ai/Qwen3-ASR-0.6B-gguf` 在 LibriSpeech test-clean（英语）上的
  WER，Q8_0 2.11% / Q4_K_M 2.26%。**只代表英语**，中文没有公开对照。

**投影（mmproj）不跟着降。** 它是音频编码器，量化它对识别质量的影响明显大于
对 LLM 部分的影响，而它只占 204 MiB —— 省它不划算，三档共用 `mmproj-Q8_0`。

## 3. 怎么选

| 场景 | 选 | 理由 |
| --- | --- | --- |
| 有独显（≥4 GiB 空闲显存） | 默认（Q8_0） | 质量最好，速度已远超实时（rtf 0.02–0.08） |
| 独显但显存吃紧（2–3 GiB 空闲） | Q6_K | 省 350 MiB，质量无可测差异 |
| 纯 CPU（无独显 / 集显） | **Q4_K_M** | 速度提升最明显的一档；CPU 上 rtf 从 0.3 量级往下压 |
| 8 GiB 内存以下的老机器 | Q4_K_M | 磁盘 + 内存一起省，避免与播放器抢页 |

判据只有一条：**先看字幕滞后是否超过一个窗口**（5 s）。滞后明显就是档位选高了。

## 3.5 换档后的第一句会晚十几秒（正常）

刚量化出来的新权重**第一次**加载时，首个音频请求实测 16.3 s（窗口 5 s），第二个立刻
回落到 1.3 s —— 大头是权重首次从磁盘搬进显存，和"模型好不好"无关。同一份权重第二次
启动（文件已在页缓存）就正常了：预热 0.77 s，10 s 音频 1.50 s，4.2 s 音频 0.59 s。

worker 启动时会喂 0.5 s 静音做一次 `warm_audio()`，把音频图首次构建（约 0.7 s）
提前付掉，消掉"第一句总比后面慢"的抖动。所以：

- **换档/换包后第一次播放**：第一句可能晚到十几秒 → 属正常；
- 之后每次启动：正常出字节奏。

## 4. 怎么生成新档（不需要联网）

本机已带 `llama-quantize.exe`，从 bf16 直接量化，CPU 完成，不占 GPU：

```bash
cd E:/WorkBuddy/3FP-AI-Subtitles/llama-b11669/cuda
./llama-quantize.exe \
  "E:/WorkBuddy/3FP-AI-Subtitles/Qwen3-ASR-0.6B-GGUF/Qwen3-ASR-0.6B-bf16.gguf" \
  "E:/WorkBuddy/3FP-AI-Subtitles/Qwen3-ASR-0.6B-GGUF/Qwen3-ASR-0.6B-Q4_K_M.gguf" \
  Q4_K_M
```

然后把新文件加进包清单的 `models`（见下）。Q2_K / Q3_K_M 也能这样出，
但**不建议**：ASR 是逐 token 生成标签与正文，低到 3 bit 以下容易出现"标签对、正文崩"
的静默劣化 —— 那种坏法比卡顿更难排查。

```json
"models": {
  "Q8_0":   { "model": "models/Qwen3-ASR-0.6B-Q8_0.gguf",   "mmproj": "models/mmproj-Qwen3-ASR-0.6B-Q8_0.gguf" },
  "Q4_K_M": { "model": "models/Qwen3-ASR-0.6B-Q4_K_M.gguf", "mmproj": "models/mmproj-Qwen3-ASR-0.6B-Q8_0.gguf" }
}
```

规则（实现见 `Ai字幕包.读模型档表`）：

- 档名任取，界面上原样显示；
- 任一路径不存在 → **整档丢弃**（宁可少一个选项，也不让用户选到注定起不来的档）；
- `mmproj` 可省略 → 取主权重旁边第一个 `mmproj-*.gguf`；
- 旧设置里记着的档名在新包里不存在 → **回落默认档并写进日志**，绝不拒绝启动；
- 清单没有 `models` → 下拉里只有"默认档"且置灰（旧包完全不受影响）。

## 5. 打包

便携包脚本会把 `models` 里每一档的权重一起搬走并改写成相对路径：

```bash
python tools/ai-subtitles/make_portable_pack.py --source <包目录> --target <目标> --copy
```

注意体积：带了 Q8_0 + Q4_K_M 两档，包会多出 ~1.4 GiB。只发低配版就把清单里
不需要的档删掉 —— 那是最省事的"裁剪"。

## 7. llama-server 参数盘点：哪些能调、哪些是默认值（2026-10-23，2026-10-25 加逃生门）

用户问"模型本身还有什么可调的（深度、Q 几等）"。把 b11669 二进制
`llama-server --help` 过了一遍，结论如下。**"能调"的标准是：改它对 ASR 字幕
这个场景有可观测的好处，且不引入未验证的质量风险。**

### 7.1 已开放（设置页可直接调）

| 参数 | 界面入口 | 语义 |
| --- | --- | --- |
| 量化档（"Q 几"） | 高级 → 模型档位 | 同一个包多档权重，换档只重启 worker（§1–§3） |
| `--n-gpu-layers`（"深度"） | 高级 → GPU 层数 | 卸载到显卡的层数。下拉预置：自动（不指定，llama-server 把 28 层全卸）/ 全部 28 层 / 24 / 20 / 16 / 12 / 8 / 4 / 0（纯 CPU）。显存吃紧往下选，如 16 = 一半权重在显存。选 CPU 后端时置灰（设备是 none，无从卸起） |
| `--device` / `--device-backend` | 推理设备 | auto = 跟随包清单 device；本机清单是 cuda，所以 auto 在该机落 CUDA0 + 全卸 |
| `--device` 序号 | 高级 → 设备序号 | 多显卡时选第几块 |
| 窗口 / 步长 | 高级 → 窗口（秒）/ 步长（秒） | 字幕切分粒度，与 llama-server 无关但同属高级区 |
| **任意 llama-server 参数** | 扩展包清单 `llamaArgs` | 换模型时的逃生门：`["--ctx-size","8192","--temp","0.4"]` 逐 token 追加，worker 固定默认值遇同名 flag 整项让位。见 `PACK_FORMAT.md` §2.5 |

**默认值为什么是 auto 而不是 CPU**：auto 的解析链是"用户没选 → 包清单 device
（cuda）→ worker 问 `--list-devices` 匹配 CUDA0 + ngl 999"。老设置文件里存过
`cpu` 的，2026-10-23 起已统一迁移为 auto；新装用户类默认就是 auto 语义。
显存被别的程序占着时 llama-server 自己会报错，回落由用户切 CPU 完成。

### 7.2 worker 支持但没往界面放

| 参数 | 现状 | 为什么不放 |
| --- | --- | --- |
| `--threads` | worker `--threads` 已实现，宿主不传 | 自动值已经合理：GPU 后端 `min(核, 8)`（只做采样与回退）、CPU `min(核, 16)`（线程直接决定速度）。再往界面放一层只会多一个"调坏了不知找谁"的入口。排障时可手动传 |

### 7.3 默认值 + llamaArgs 逃生门（2026-10-25 起不再是绝对锁死）

这些参数 worker 带固定默认值，**默认不放界面**；换非 Qwen3-ASR 模型时可用扩展包
清单的 `llamaArgs` 覆盖（同名 flag 整项让位，见 `PACK_FORMAT.md` §2.5）。下表
"默认值依据"栏就是逃生门的正确用法说明——有依据的例外才该覆盖：

| 参数 | 当前值 | 默认值依据（覆盖前先对照自己的场景） |
| --- | --- | --- |
| `--temp` | 0.6 | 直接决定转写质量（更确定 vs 更多样）。没有质量评测就不该动——字幕错了用户立刻看得见，而" temperature 调到 0 更稳"只是直觉 |
| `--ctx-size` | 4096 | 5 s 窗的 prompt 只有几百 token，4096 余量巨大；调大只白吃 KV。换用长上下文模型 / 更长窗口时才值得调 |
| `--cache-ram 0` + `--no-cache-idle-slots` | 已启用 | **这是针对 ASR 的优化**：每个窗的音频都不同，前缀复用纯浪费。实测默认 cache-ram 8192 会在 15 分钟里涨 2.1 GB RSS（VRAM 平坦），两个 flag 一起才压住 |
| `--batch-size` / `--ubatch-size` | 默认 2048/512 | ASR 是单请求串行，没有并发批可批 |
| `--flash-attn` | auto（二进制默认） | 0.6B + 4k ctx 的收益不成比例，兼容风险（老驱动）倒是一票否决 |
| `--cache-type-k/v`（KV 量化） | 不量化 | KV 本来就小（4k ctx × 0.6B），省不出显存，白搭精度风险 |
| `--mmap` / `--mlock` | mmap（默认） | mmap 惰性上传正是"换档首窗晚十几秒"的原因（§3.5），但那是**首次加载**的一次性代价；强制 mlock 会让常驻内存实打实涨，字幕场景没有对应收益 |

### 7.4 怎么验证这些数字

```bash
# 看这台机器有哪些设备（零推理成本）
llama-server.exe --list-devices

# 层数/量化档的实机对照：手动起服务，看加载日志里的 offload 行
llama-server.exe -m <model> --mmproj <mmproj> --n-gpu-layers 16 --device CUDA0
```

改任何默认值之前，先想清楚"它改变哪个结论"——这一节的每一项都对应一次实测或一个
明确的失败模式，没有"据说更好"的位置。真要覆盖时走清单 `llamaArgs`
（`PACK_FORMAT.md` §2.5），并在覆盖前用上面的命令对照自己场景。

## 6. 未验证 / 风险

1. **Q4_K_M 的中文精度没有实测**。第三节的选型建议基于英文 WER 与 CPU 速度经验，
   中文若出现错字变多，回 Q6_K 即可。
2. **Q4_K_M 的稳态显存占用未实测**（mmap 惰性上传，`nvidia-smi` 增量不可信）。
3. 上表速度只有 CUDA 臂的数字。**CPU 臂没跑 Q4_K_M** —— 它是这档最主要的目标场景，
   值得在弱机上补一次（一档一次即可，不必做矩阵）。
3. 更低档（Q3_K_M 及以下）**没有做**，也不建议做：静默劣化风险高。
