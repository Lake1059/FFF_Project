# AI 字幕验收清单：交互矩阵 + 量化基线

> 两部分，别只跑一半：
>
> 1. **交互矩阵**（下面 31 项）——P4 门禁里唯一还挂着的项（seek / 暂停 /
>    切文件 / 关闭时的字幕清屏）。这些链路已经实现，缺的只是实测证据。
> 2. **量化基线**（文末一节）——交互矩阵的判据几乎全是「日志里有某行」或
>    「目视」，只能证明**字幕出来了**，证明不了**字幕对不对、快不快**。那一节
>    用真实影片片段直接打转写端点，给出可比对的数字（RTF、语种、失控护栏）。
>
> 2026-10-25 补上量化基线的原因：拿真实影片跑第一遍就抓到两个交互矩阵永远
> 发现不了的问题——无语音段让模型编出 3808 个「啊」，以及默认参数下 RTF 高达
> 6.7（字幕永远追不上画面）。

## 为什么只能手工

这些操作要往运行中的播放器发按键。本环境下自动化两条路都断了：

- `cscript` / `wscript` 被安全策略当 LOLBin 拦掉，`SendKeys` 发不出去；
- 截屏取证不可行：schtasks 派发的窗口不在 gdigrab 能抓的桌面上。

所以只能人坐着点，用**日志**当证据。日志本身是机器可验的
（`字幕[代次 N]`、`generation -> N`、`字幕图层状态 …`），不需要截图。

## 准备

1. 装好扩展包，AI 字幕能正常出字（见 `USER_GUIDE.md` §2–§3）。
2. 日志随看随 tail：`<3FP 程序目录>\ai-subtitles.log`。
3. 素材：任意中英对白、时长 ≥ 1 分钟的视频；另备一个无音轨文件。

### P0：切文件 / 切换解码器 → 会话损坏（黑屏 + 播放中断 + AI 字幕永久沉默）

**这是「切换 GPU/CPU 解码黑屏」的同一个根因，两条路径共用 `切换媒体会话`。**

实测（2026-10-25，切 `en-lecture.webm` → `zh-en-mix.webm`）：

- 08:25:47 `generation -> 0` 之后：`字幕图层状态` 恒为 `呈现帧数=0 已绘制序号=88 命令数=0 画布=0x0`，
  worker 持续正常出 `final`（rtf 0.04~0.09，中文"你好/早早早"都识别对了），
  **但没有任何一条 `字幕[代次 N]` 上屏**，持续 4 分钟以上；
- 追加 seek 无效：无 `generation -> N`，worker 的 final 时间连续推进（55→60→…→95 s）未被重置 →
  seek 没到达内核；
- **对照实验**：关掉播放器、重启后直接打开同一个 `zh-en-mix.webm`，字幕完全正常
  （`字幕[代次 0] 你好。`、rtf 0.038~0.074、`呈现帧数=3347 命令数=1`）。
  → 缺陷**只在「切文件/切解码器」这条路上**，与文件、模型、worker 都无关。

根因链（`切换媒体会话` 全量换会话路径，`播放器控制器.vb:1235-1338`）：

1. `播放器控制器.vb:1253` 新会话构造时 `输出窗口句柄 = IntPtr.Zero`（`:1407`）——headless；
2. headless 期间 `Render` 在 `VideoRenderer.cpp:6817-6820` 提前返回（`window_ == nullptr`），
   **不上传、不 bump `hasCachedVideo_`**，headless seek 解出的目标帧被丢弃；
3. `播放器控制器.vb:1299` `重绑输出窗口()` → `SetOutputWindow` 里普通视频只有 `Redraw()`
   （`PlayerSession.cpp:1697-1702`），而 `Redraw` 在 `VideoRenderer.cpp:7202`
   `!hasCachedVideo_` 时**必然空转**；静图/封面有补偿渲染，普通视频没有（不对称）；
4. 若切换前非 Playing 态，`:1300` 的 `恢复播放` 为 False → `PlayerSession.cpp:2772-2793`
   Worker 不跑 `PumpPlayback` → **再没有任何路径呈现一帧 → 永久黑屏**；
5. `重绑输出窗口()` 的 `Catch ex As 播放器异常` 静默吞掉（`:1066-1073`）——
   同一 HWND 上旧 flip chain 未 retire 完时 `CreateSwapChainForHwnd` 可被 DXGI 拒绝
   （`PlayerSession.cpp:3368-3370` 注释自证），用户看不到任何提示。

对 AI 字幕的连带效应：新会话无窗口 → 字幕图层不 present（`呈现帧数=0` 冻结），
叠加宿主侧播放位置/代次与新文件错位，`Ai字幕状态机.vb:153`（代次守卫）/ `:167`（陈旧守卫）
把新文件全部结果判死 → 字幕永久沉默（seek 也救不回来，因为 seek 同样到不了内核）。

修复方向（按代价排序，**均未落码，待确认**）：

- **A（最建议）**：`SetOutputWindow` 的 `Redraw` 分支扩展为"有队列帧/最近帧时主动 Render 一帧"
  （`PlayerSession.cpp:1697-1702`），或在 `重绑输出窗口()` 后无条件完成一次首帧呈现；
- **B**：`重绑输出窗口()` 失败不得静默吞——至少记日志 + 重试一次（等旧 chain retire）；
- **C（收窄）**：`播放器AI字幕控制器.vb:312` 的 `状态机.重置()` 改为仅代次变化/首启时执行。

### 附带发现（不阻塞，已记录）

- **E 盘扩展包目录 `tmp` 建不了**：每 5 s 一条 `临时目录候选不可写 … UnauthorizedAccessException`

## 怎么判失败

- **第 2、6 项最关键**：代次守卫的全部意义就是"seek/切文件后旧字幕立刻作废"。
  如果旧字幕停留一两秒才消失，说明代次没有及时变化（内核 tap 的 `generation`
  或宿主 pump 的传递断了）。
- **第 4 项**如果字幕闪掉，说明陈旧守卫把"暂停"误判成"推理卡住"了——暂停时
  播放位置不动，条目不应当过期。
- 任何一项失败，把日志末 50 行附上；里面有 worker 每次 `final [...]` 与代次变化，足够定位。

### 已知会踩的坑（别当产品 bug）

- `zh-wiki.ogv` 音轨语音稀疏，多处识别为「嗯。」/「啊！」，还会**原样吐出
  `Transcribe audio to text` 模板串**——模型在近乎无语音时会把 instruction 当
  内容输出。这不是产品 bug，但**上屏就是污染**，所以 worker 判它为「指令泄漏」
  并丢弃（判据只杀短得像一句指令的英文文本，中文长句里夹这句话不会误杀）。
  这段素材正好用来验 Q8，不适合当中文准确率基线。
- `zh-interview.webm`（AV1 + Opus）seek 到某些时间点抽不出音频，生成 78 字节空
  wav，llama-server 对空音频回 HTTP 400。抽样时避开。
- **无语音段本身也慢，别拿它当性能结论**：吐模板串的那一窗实测 9.4 s / 27.8 s
  （rtf 1.9 / 5.6），因为模型会把生成预算走完；正常语音窗是 0.29~0.38 s
  （rtf 0.058~0.076）。差异是两个数量级，采样时先确认这窗到底有没有人声。
- **别拿前两次的数字当性能结论**：那是冷启动（Q2）。
- 一次只跑一个 llama-server 实例。两个实例同时跑会争抢 GPU，同一段音频的耗时
  能差出好几倍，结论会被带偏。
