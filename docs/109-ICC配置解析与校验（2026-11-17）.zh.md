# 109 · ICC 配置解析与校验接入内核（2026-11-17）

本轮把 `fff::icc::Parse`（结构化解码器）接进 `BuildImageInfo` 的影像信息链路，并追加一个 ABI-safe 的 JSON 导出 `FFF3FP_GetIccProfileInfo`。目标只有一个：让「有效 ICC」成为可判别的事实——**只有结构校验通过的 profile 才会被上报为"已识别"**，畸形/非 ICC 字节不再冒充"ICC ok"。

> 本轮做**解码、校验与只读色度摘要**，不做任何像素色彩变换。不引入 lcms2；`CicpSupport.h` / `VideoRenderer.cpp` 的既有白名单语义不变。色度摘要直接扩展 `IccProfileParser`（不新增 `IccColorimetry` 副本），保证 parser 是唯一真值。

---

## 1. 支持边界

解码器 `FFF.Native/3FP/Core/IccProfileParser.{h,cpp}` 按 tag type 分三档处理。

### 1.1 结构化解码（payload 被解析成类型化字段）

| tag / type | 内容 |
|---|---|
| `desc`（v2）、`mluc`（v4）、`text`、`utf8`、`sig`、`data` | 文本/签名，写入 `TagInfo.text`；mluc 另存多语言别名 |
| `curv` | 曲线：count=0 恒等、count=1 gamma(u16Fixed8)、否则 LUT；LUT 值按剩余字节识别 16 位/8 位并存入 `CurveInfo.table` |
| `para` | 参数化曲线：function type 0..4 + g/a/b/c/d/e/f（参数从 offset 12 起） |
| `XYZ ` | 三次值（wtpt/rXYZ/gXYZ/bXYZ/lumi 等）→ `XyzInfo` |
| `sf32` | S15Fixed16 数组（chad 3×3、lumi 1 个）→ `fixed` |
| `cicp` | ICC.1:2022 colourimetryType：primaries / transfer / matrix / full-range 四个字节 |
| `meas` / `view` / `chrm` / `clro` / `clrt` | 标量数组 → `u16` |
| `mft1` / `mft2` | 矩阵-shaper LUT（输入/输出通道、网格点、合法性） |
| `mAB ` / `mBA ` | CLUT LUT（通道数、网格、合法性、问题描述） |
| `ncl2` | 命名色表 |
| `dtim` / `scrn` / `bfd ` | 日期/加网/UCR-BG 的边界与类型识别 |

派生便利量：`description`、`copyright`、`hasMatrixColumnTags`、`hasChad`、`hasWhitepoint`、`hasLut`、`isNamedColorProfile`，以及本轮新增的 `colorimetry`：
- `hasRgbToXyzD50` / `rgbToXyzD50[9]`：`rXYZ`/`gXYZ`/`bXYZ` 三列齐全时组装 RGB→XYZ(D50) 行主序矩阵；
- `hasWhitePoint` / `whitePoint`：`wtpt`；`hasChad` / `chad[9]`：`chad`；
- `hasRgbCurves` / `rCurve`/`gCurve`/`bCurve` / `curvesIdentical`：三通道 TRC 原始曲线；
- `knownSpaceName` / `primariesToken` / `transferToken` / `knownSpaceError`：与内置 sRGB / BT.2020 / Display P3 / DCI-P3 / Adobe RGB / ProPhoto RGB / ColorMatch RGB / BT.601-625 / SMPTE 170M 的 D50 理论矩阵比较（阈值 2e-3），并从 `para`/gamma 曲线认领 sRGB/BT.709/γ2.2/γ2.8；
- `hasCicp` / `cicp`：`cicp` tag 原始四字节与 token 映射；ICC 矩阵/TRC 命中时优先于 CICP，缺失时才回退 CICP。

### 1.2 仅 raw（边界校验通过，payload 不展开）

- 任何**未知 / 厂商私有** tag：tag table 里的 offset/size 做了越界与重叠校验，字节原样留在文件里，`rawOnly=true`。
- 这是刻意选择：私有 tag 的载荷语义不公开，强行解码既无收益也有风险。未知 tag **不是错误**。

### 1.3 明确拒绝（`usable=false`，整份 profile 判无效）

只有**结构性违规**才让一份 profile 不可用；内容/偏好层面的差异不算：

- `NotIcc`：偏移 36..39 没有 `acsp` 签名；
- `HeaderTooSmall`：少于 128 字节；
- `ProfileTooLarge`：声明大小超过调用方预算（默认 8 MiB，远超真实 display profile）；
- `SizeMismatch`：声明大小 ≠ 实际提供字节数；
- `VersionUnsupported`：主版本不在 {2, 4}；
- `TagTableTruncated`：tag 计数/表越出文件；
- `TagOutOfBounds`：tag 数据落在 profile 之外；
- `TagOverlap`：两个 tag 声称重叠的载荷区间；
- `TagDataTruncated`：tag 声明大小小于其 type 头；
- `MalformedTag`：某个被解码 tag 内部结构损坏（坏 LUT/curve、文本编码非法等）。

## 2. v2 与 v4 差异

- **描述 tag**：v2 用 `desc`（ASCII + Unicode + ScriptCode 三段），v4 用 `mluc`（多语言 Unicode）。两者都被解码进 `description`。
- **版权 tag** 同理（`cprt` 的 type 随版本不同）。
- **版本字段**：`versionRaw` 是完整 32 位版本域；主版本取 byte 8，次版本取 byte 9 的 **高 BCD nibble**，revision 取低 nibble。`04 40 00 00` 必须报 `4.4`（此前的 `>>16 & 0xFF` 会误报 `4.64`，已修）。JSON 里报 `"version":"2.x"` / `"4.x"`。
- 头其余字段（class、data space、PCS、平台、渲染意图、illuminant D50、creator、profileId）两版共用同一套解码。
- 解码器不假设某版本"必须有"哪些 tag；缺 tag 只体现为对应派生量为 false/空，不报错。

## 3. 拒绝矩阵（与 `BuildImageInfo` 的行为对应）

| 帧侧数据 | `Parse` 结果 | `iccProfileSizeBytes` | `FFF3FP_IMAGE_FLAG_HAS_ICC` | 导出 JSON 的 `status` |
|---|---|---|---|---|
| 无 `AV_FRAME_DATA_ICC_PROFILE` | 不调用 | 0 | 不置 | `"absent"` |
| 有侧数据但 `usable=true` | `Ok` | 实际字节数 | **置** | `"Ok"`，`usable=true` |
| 有侧数据但 `usable=false` | 上述任一拒绝原因 | 实际字节数 | **不置** | 对应状态名，`usable=false` |

要点：
- **字节数如实上报**——侧数据在不在，与它合不合法是两回事；`size>0` 但 `HAS_ICC` 未置 = "有附件但校验未过"。
- 解析失败**不崩、不抛**：`BuildImageInfo` 是 `noexcept`，内部 `try/catch` 兜底（解析器契约本身不抛，这里只防 `bad_alloc` 等意外）。失败原因存在会话成员 `lastIccStatus_`（即 `StatusName(status)`）。
- **不进 16 KiB side-data 环**（`MaximumCachedSideDataBlobBytes`，注释明写 ICC 太大且对色彩分析无用）。ICC 走独立成员 `publishedIccProfile_`，预算不改。

## 4. 导出契约（ABI-safe 追加）

头文件 `FFF.Player.Api.h` 在 `FFF3FP_GetImageInfo` 之后追加：

```c
FFF3FP_API FFFResult FFF3FP_GetIccProfileInfo(
    FFF3FPHandle player, char* outputUtf8,
    std::uint32_t outputSize, std::uint32_t* requiredSize) noexcept;
```

- **不改任何既有结构体布局、不 bump API 版本**（`PlayerApiVersion` 仍为 20）。旧内核没有此导出时宿主 `GetProcAddress`/P/Invoke 失败，按"不可用"回落。
- 缓冲语义照抄 `FFF3FP_GetMediaInfo` / `CopyUtf8`：
  - `*requiredSize` 总是返回含 NUL 的字节数；
  - `outputUtf8==nullptr` 或 `outputSize < required` → 返回 `BufferTooSmall`，不写缓冲；
  - 足够 → 拷贝并返回 `Success`。
- **无 profile 也是合法 JSON**：返回 `{"status":"absent"}`（`Success`），不是错误码。
- 有 profile 时返回 `fff::icc::ToJson` 的单行 ASCII 安全 JSON：`status/message/usable/version/class/dataSpace/pcs/tagCount/tagDecoded/tagRawOnly/tagFailed/description/copyright/hasLut/hasChad/hasCicp/cicp/colorimetry/tags[]`。`colorimetry` 含 D50 矩阵、白点、chad、三通道曲线、已知空间名/primaries/transfer token 与匹配误差；每个 tag 另带 `xyz` / `curve` / `cicp` / `fixed` 的类型化字段。`ToJson` 的 `usable` 分隔符曾写成 `"usable\`（产出非法 JSON），本轮修正为 `"usable":`，并对全部 32 个语料用严格 JSON parser 验证通过。

宿主侧：
- `播放器原生接口.vb` 追加 `FFF3FP_GetIccProfileInfo` 的 `DllImport`（照 `GetMediaInfo` 风格，`ByRef 所需大小`）。
- `播放器会话.vb` 追加 `Friend Function 取ICC信息() As String`，复用既有 `读取原生文本(AddressOf …)` 两段式；任何异常返回空串并 `Debug.WriteLine`，不抛给 UI。
- **未改** `原生图片信息` 结构体布局，**未改** `取图片信息()` 签名。

## 6. 后续（不在本轮）

- **ICC → 显示变换**：本轮只产出矩阵/曲线/白点/chad/CICP 的结构化摘要；像素变换仍需 3×3 矩阵 / CLUT 求值或 lcms2，明确不做。摘要字段已经是下一轮变换的输入。
- **非中性 TRC**：三通道曲线原样保留，`curvesIdentical=false` 且 `transferToken` 留空，不把非中性 profile 伪装成单曲线。
- **LUT-based profile**：`mft1/mft2/mAB/mBA` 只校验结构，不建 CLUT 采样表；CMYK/LUT 显示 profile 的像素正确性仍需单独变换路径。
- **G7 UI 展示**：宿主详情 API（`取ICC信息()`）已落地，但 UI 上展示版本/类别/描述/校验结论另排期。
- **G5 色彩解析**：`ResolveAppliedMediaColor` 仍只看 CICP 三源；何时让它"在 CICP 未指定时回退到可用 ICC"，与变换议题一起决策。
